# ADR-0050: 職員に結び付いた上流のアカウントを、マネージャーは職員の詳細の画面から、運営者は運営用の CLI から外し、外したらログインのセッションを取り消す

## Status

承認

## Context

職員に結び付いた上流のアカウントを、退職させずに外す手段が要る。  
誤ったアカウントで結び付いた職員が、正しいアカウントで入り直せるようにする。

- ブローカーは、初回のログインで、上流の IdP のメールが確認済みで登録のメールと同じときに、上流のアカウント（`iss` と `sub`）を職員に結び付ける。結び付け済みの職員は `iss` と `sub` で照合し、メールを見ない。
  - ADR-0001: [認証を OIDC のブローカーと BFF のサーバー側のセッションにし、職員の身元をブローカーが、権限と業務のデータを予定の API が持つ](0001-auth.md)
- 結び付けを外すのは、退職だけである。休職と復職では外さない。退職は戻せない。
  - ADR-0004: [職員の停止を、戻せる休職と、戻せない退職に分ける](0004-staff-leave-and-retirement.md)
- 事業所の上流の IdP の設定に許すドメインを足すと、ブローカーは `hd` が合わないログインを、結び付け済みの職員も含めて拒む。許すドメインを足す前に個人の Google のアカウントで結び付いた職員は、ログインできなくなる。
- ブローカーは、上流のアカウントの `iss` と `sub` だけを持ち、`hd` と上流のメールを持たない。許すドメインと合わない結び付けを、今のデータで一覧にできない。
- 休職と退職では、ブローカーが Hydra のログインのセッション、同意、refresh token を取り消す。Hydra のログインのセッションは 12 時間続く。
- 職員の休職と退職は、職員の管理の権限（`staff.manage`）を持つ職員が、予定の API で行う。予定の API が権限を確認してから、ブローカーの内部の API を呼ぶ。
- 運営者は、運営用の CLI で事業所と最初のマネージャーを登録する。マネージャーが操作できなくなった事業所には、明示のフラグで別のマネージャーを足せる。
  - ADR-0052: [事業所と最初のマネージャーを予定の API の運営用の CLI で登録し、ブローカーは運営用のクライアントに職員の登録と結び付けを外す操作だけを許す](0052-facility-onboarding-cli-unlink.md)
- 職員の権限の変更と運営者の登録は、予定の API の DB の監査の記録に、操作と同じトランザクションで残す。
  - ADR-0051: [権限の変更と結び付けを外す操作を、操作した職員か運営者と変更の前後で、予定の API の DB の監査の記録に残す](0051-permission-audit-unlink.md)

## Decision

### 外せる人と手段

- 職員の管理の権限を持つ職員は、職員の詳細の画面から、同じ事業所の職員の結び付けを外せる。
  - 理由: 誤ったアカウントに気づくのは事業所の側で、休職と退職と同じ権限にそろう。
  - 自分の結び付けも外せる。外すとログアウトし、次のログインで結び付け直すだけで、権限も状態も変わらないためである。許すドメインを足す前に、事業所でただ 1 人のマネージャーが自分のアカウントを直せる。
- 運営者は、運営用の CLI で、職員の結び付けを外せる。
  - 理由: 許すドメインを足した後に、事業所でただ 1 人のマネージャーが拒まれると、事業所の中に外せる人が残らない。
- 外せる職員は、有効と休職の職員である。退職した職員と登録の途中の職員は結び付けを持たないので、何もせずに成功する。

### 外す流れ

- 予定の API は、権限を確認してから、ブローカーの内部の API で結び付けを外させる。
- ブローカーは、上流のアカウントの結び付けを消してから、休職と同じく Hydra のログインのセッションと全てのクライアントへの同意を取り消す。同意を取り消すと、Hydra はその同意から発行した access token と refresh token も取り消す。
  - 理由: 取り消さないと、誤ったアカウントの持ち主が 12 時間まで使い続ける。その間、Hydra は保ったセッションでログインさせるので、正しいアカウントで結び付け直せない。
  - 何度呼んでも成功する。結び付けを消した後に取り消しに失敗したときは、`revoke_failed` の 502 を返し、送り直しで取り消しをやり直させる。
- 予定の API は、監査の記録（`staff.unlink`）を書いてから、同じトランザクションの中でブローカーを呼び、コミットする。
  - ブローカーが失敗すれば、記録も戻す。
  - コミットだけが失敗すると、結び付けは外れたまま記録が残らない。送り直すと、ブローカーは何もせずに成功し、記録を書く。
- 外した職員は未結び付けに戻り、次のログインで、登録のメールに当たる上流のアカウントで結び付け直す。結び付け直す条件は、初回のログインと同じにする。

### 許すドメインを足す前の確認

- 運営者は、事業所の上流の IdP の設定に許すドメインを足す前に、事業所のマネージャーに、職員ごとのログインのアカウントを確認してもらう。許すドメインと合わないアカウントで結び付いた職員は、マネージャーが外す。
- 確認から漏れた職員は、許すドメインを足した後に拒まれる。運営者は、ブローカーの拒んだログインのログ（`hd` を含む）から職員を探し、マネージャーに外してもらう。
- 手順は、運営の context の事業所を足す手順に書く。

## Considered Options

| 論点 | 選択肢 | 強み | 弱み |
| --- | --- | --- | --- |
| 外せる人 | **採用:** マネージャーと運営者 | ふだんは事業所の中で直せる。ただ 1 人のマネージャーが拒まれても、運営者が外せる | 運営用のクライアントに許す操作が増える |
| 外せる人 | マネージャーだけ | 運営用のクライアントを広げない | ただ 1 人のマネージャーが拒まれると、運営者が別のマネージャーを足さないと戻せない |
| 外せる人 | 運営者だけ | 外す操作が事業所の外の 1 か所に集まる | 事業所は運営者に頼むまで直せない |
| 外した後 | **採用:** ログインのセッション、同意、トークンを取り消す | 誤ったアカウントの持ち主がすぐに使えなくなる。正しいアカウントで結び付け直せる | 外された職員はログアウトする |
| 外した後 | 取り消さない | ログイン中の職員が止まらない | 誤ったアカウントで 12 時間まで使い続けられ、その間は結び付け直せない |
| 設定の前の確認 | **採用:** マネージャーが職員ごとのアカウントを確認して外し、確認から外れた職員はログから探す | 今のデータのまま手順を書ける | 確認は人の手で、確認から外れる職員が出ることがある |
| 設定の前の確認 | 結び付けのときに `hd` を保存し、合わない結び付けを一覧にする | 機械で一覧にできる | 今ある結び付けには `hd` が無く、新しい結び付けからしか使えない |
| 設定の前の確認 | 確認せず、設定の後にログから探す | 手順が少ない | 拒まれるまで職員が気づかない |

## Consequences

### Positive

- 誤ったアカウントで結び付いた職員を、退職させずに正しいアカウントで入り直させられる。
- 許すドメインを足す事業所で、個人のアカウントで結び付いた職員を戻せる。
- 誰がいつ外したかが、監査の記録に残る。

### Negative

- 結び付けを外すと、その職員はログアウトする。
- 運営用のクライアントの secret が漏れると、職員の結び付けを外して、ログアウトさせられる。
- 許すドメインを足す前の確認は、マネージャーの手の作業である。
