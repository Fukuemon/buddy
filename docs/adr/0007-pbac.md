# ADR-0007: 権限を役職のデフォルトと職員ごとの上書きで持ち、職員の管理と照合も権限で許す

## Status

承認

## Context

職員が扱える予定の範囲は、[PRD の役職ごとの権限](../PRD.md#役職ごとの権限)にある 7 つの予定の権限で決まる。

- 同じ役職でも、職員によって見てよい予定が違う。例として、チームに属さない職員の予定を、特定のメンバーにだけ見せる。
- 予定の権限のうち 4 つは、対象の職員かチームを指定する（指定した職員の予定の閲覧など）。
- 管理者は、職員を登録するたびに権限を 1 つずつ選びたくない。
- 権限の context は、判定に役職を直接使わず、職員の権限（`user_policies`）だけを読むと決めている。
- 権限を足し外す操作と役職を変える操作で、職員が自分に権限を足すことを許すと、予定の判定の意味が無くなる。
- 事業所で照合をするのは事務の職員で、事務の職員は訪問せず、照合の食い違いを予定表で直す。
- 職員が buddy で何をしてよいかは予定の API が持ち、ブローカーは権限を持たない。照合の API は、職員を探さずに、トークンの組織だけで事業所を決める。
  - ADR-0001: [認証を OIDC のブローカーと BFF のサーバー側のセッションにし、職員の身元をブローカーが、権限と業務のデータを予定の API が持つ](0001-auth.md)
- web の BFF は、職員の access token を Bearer で付けて、照合の API と予定の API を呼ぶ。1 つの access token の `aud` に、`schedule` と `receipt` の両方が入る。
- ブローカーは、Hydra の `oauth2.token_hook` に 204 か 403 だけを返す。200 を返すと、Hydra は access token の追加のクレームを置き換え、同意で入れた `org_id` が消える。
- 照合の API は、web の BFF を通らずにも呼べる。ドキュメントサイトの API の仕様のページと、手で取ったトークンからも呼べる。
- 予定の API の `GET /v1/me` は、トークンの職員と、その職員の権限を返す。休職と退職の職員には 403 を返す。
- 事業所を作る API は無い。事業所の役職は、運営側が事業所を足すときに作るか、職員の管理の権限を持つ職員が役職の作成の API で作る。

## Decision

### 権限の持ち方

権限を `policies` のレコードとして持ち、職員ごとに付ける（PBAC）。役職は、職員に付ける権限のデフォルトだけを持つ。

- `policies` は 9 つの権限を持つ。7 つの予定の権限、職員の管理（`staff.manage`）、照合（`receipt.check`）である。`position_policies` は、役職ごとのデフォルトの権限を持つ。
- 職員を登録したときと役職を変えたときに、予定の API は役職のデフォルトの権限を `user_policies` にコピーする。役職を変えたときは、職員の `user_policies` を消し、新しい役職のデフォルトの権限をコピーし直す。
- 職員の管理の権限を持つ職員は、その後に職員の `user_policies` を足し、外せる。認可は `user_policies` だけを読む。
- 対象を指定する権限は、`user_policy_targets` に対象の職員かチームを持つ。役職のデフォルトの権限からコピーするときは、チームの対象を職員の所属のチームにする。

認可の評価を `user_policies` の 1 か所にすると、職員の権限の一覧が DB のレコードのまま画面に出せる。

### 職員の管理の権限

職員の管理（`staff.manage`）は、対象を指定しない権限（`needs_target` が false）で、マネージャーの役職のデフォルトの権限にする。  
職員と利用者の登録、役職の作成、職員の権限を足し外す操作、役職を変える操作は、この権限を持つ職員だけに許す。  
役職の作成を含めるのは、役職にデフォルトの権限を付けると、その役職の職員に権限を配れるためである。

- 役職ではなく権限で判定するので、権限の context の禁止に合う。
- 予定の権限とは範囲が違うので、7 つの予定の権限の判定の規則は変えない。
- 職員の管理の権限を持つ職員は、自分を含む職員に任意の権限を足せるので、事実上の最上位の権限である。自分への付与は止めない。

### 照合の権限

照合（`receipt.check`）は、対象を指定しない権限（`needs_target` が false）である。照合の API の照合（`POST /v1/checks`）は、予定の CSV で照合するときも対象の月で照合するときも、この権限を持つ職員だけに許す。

- 照合の API は、受けた access token をそのまま付けて予定の API の `GET /v1/me` を呼び、返った権限に照合があるかで判定する。無ければ 403 を返す。予定の API が 401 か 403 を返したときも 403 を返す。
  - 理由: 権限を持つのは予定の API である（ADR-0001）。トークンにクレームとして入れると、ブローカーが権限を読むことになり、ログインが予定の API に依存する。BFF だけで確認すると、BFF を通らない呼び出しを拒めない。
  - 照合は月に数回の操作なので、照合のたびに予定の API を 1 回呼んでも負荷は問題にならない。
- 照合の画面と照合の結果の画面は、照合の権限を持つ職員にだけ出す。web は `GET /v1/me` の権限で出し分け、拒むのは照合の API である。
- 照合の権限は、職員の管理の権限を持つ職員が、ほかの職員にも職員ごとに足せる。

### 標準の役職とデフォルトの権限

標準の役職は、マネージャー、チームリーダー、メンバー、事務の 4 つである。標準の役職は、事業所を足すときに作る役職で、名前は事業所ごとに変えてよい。判定は役職を使わないので、名前を変えても判定は変わらない。

役職のデフォルトの権限のうち、事務の役職と違いがあるものは、次のとおり。

| 権限 | マネージャー | チームリーダー | メンバー | 事務 |
| --- | --- | --- | --- | --- |
| 自分の予定の編集 | あり | あり | あり | なし |
| 事業所の全ての予定の閲覧 | あり | なし | なし | あり |
| 事業所の全ての予定の編集 | あり | なし | なし | あり |
| 照合 | あり | なし | なし | あり |

- 事務の役職に、事業所の全ての予定の閲覧と編集を付ける。照合の食い違いを予定表で直すためである。
- 事務の役職に、自分の予定の編集を付けない。訪問しない職員は予定を持たないためである。
  - ADR-0006: [訪問するかを職員に持ち、訪問しない職員を予定と担当から外す](0006-non-visiting-staff.md)
- 表にない権限（指定した職員と、指定したチームの職員の予定の閲覧と編集、職員の管理）の各役職のデフォルトは、PRD の役職ごとの権限の表のとおりで、事務の役職には付けない。

## Considered Options

### 権限の持ち方

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 役職のデフォルトの権限を職員にコピーし、職員ごとに上書きする | 評価が 1 か所で、職員の権限がそのまま読める。対象の職員とチームを指定できる | 役職を変えると、職員ごとに足した権限が消える |
| 役職だけで権限を決める（RBAC） | テーブルが少なく、評価が簡単 | 「指定した職員」を表せない。例外ごとに役職を増やすことになる |
| 役職のデフォルトの権限をコピーせず、評価のたびに役職のデフォルトの権限と職員ごとの差分（許可と拒否）を合成する | 役職を変えても職員ごとの差分が残る | 評価と画面の表示の両方で合成が要り、拒否と許可の優先の規則を決める必要がある |
| 汎用のポリシーエンジン（OPA、Casbin など）に規則を書く | 属性による複雑な規則を書ける | この数の権限には過剰で、規則がアプリの外の言語に分かれる |

### 職員の管理を許す職員

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 職員の管理の権限を足す | 判定が `user_policies` だけを読むまま、マネージャー以外にも職員ごとに許せる | 権限が増え、PRD の表とデフォルトの権限を直す |
| 役職がマネージャーの職員に許す | 表を変えない | 判定に役職を使い、権限の context の禁止に反する。役職の名前は事業所ごとに違う |
| 事業所の全ての予定の編集の権限を持つ職員に許す | 権限を足さない | 予定の権限を、職員の管理という別の範囲に流用する |
| 事業所の職員なら誰でも許す | 判定が要らない | 職員が自分に全ての権限を足せる |

### 照合と事務の役職

| 論点 | 選択肢 | 強み | 弱み |
| --- | --- | --- | --- |
| 照合の判定 | **採用:** 照合の API が、受けたトークンで予定の API の `GET /v1/me` を呼ぶ | 権限を予定の API だけが持つまま、照合の API で拒める。権限を外すと次の照合から拒む | 照合の API が予定の API に依存し、予定の API が止まると照合できない |
| 照合の判定 | ブローカーが token_hook で権限をトークンのクレームに入れる | 照合の API が外部を呼ばない | ブローカーが権限を読み、ログインが予定の API に依存する（ADR-0001 で採らなかった案）。権限を外しても、トークンを取り直すまで照合できる |
| 照合の判定 | web の BFF だけで確認する | 照合の API を変えない | BFF を通らない呼び出しを拒めない |
| 照合の判定 | 予定の API に照合の権限の確認だけの API を足す | 返す内容が少ない | `GET /v1/me` で足りる判定のために API が増える |
| 事務の役職 | **採用:** 4 つ目の標準の役職 | 事業所を足すときに、照合の担当にすぐ役職を付けられる | 標準の役職とデフォルトの権限の表が大きくなる |
| 事務の役職 | 標準にせず、事業所が役職の作成で作る | 標準の役職を変えない | 事業所ごとに、照合と全ての予定の権限を付けた役職を作る手順が要る |

## Consequences

### Positive

- 職員ごとの例外を、役職を増やさずに表せる。
- 認可は `user_policies` と `user_policy_targets` を読むだけで決まる。
- 職員の管理を、役職によらず職員ごとに与えられる。
- 照合と照合の結果を、照合の権限を持つ職員だけが扱える。BFF を通らない呼び出しも拒める。照合の権限を外すと、その職員の次の照合から拒む。

### Negative

- 役職を変えると、管理者が足した権限が消える。画面は、役職を変える前に、消える権限を管理者に示す必要がある。
- 役職のデフォルトの権限を変えても、既にいる職員の `user_policies` は変わらない。既にいる職員に適用するには、役職を付け直す操作が要る。
- 事業所で職員の管理の権限を持つ最後の職員が、それを失うと、その事業所で権限を足し外せる職員がいなくなる。外す操作のほか、その職員の役職を変えてデフォルトの権限をコピーし直したときにも起きる。止めないので、戻すには DB で `user_policies` にレコードを足す。
- 照合の API が予定の API に依存する。予定の API が止まっていると、予定の CSV での照合もできない。照合の API の起動の設定に、予定の API の URL が要る。
- 照合の権限を持つ職員は、事業所の全ての利用者の名前を含む実績と照合の結果を扱える。照合の権限を足すときに、職員の管理の権限を持つ職員がそれを知っておく必要がある。
