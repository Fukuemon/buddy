# ADR-0042: 権限の変更を、操作した職員か運営者と変更の前後の権限の全量で、予定の API の DB の監査の記録に残す

## Status

承認

## Context

職員の管理の権限を持つ職員は、配れる権限に上限が無く、自分の権限も変えられる。誤りと乱用は事前に止めず、後から追う。

- ADR-0041: [権限を役職のデフォルトと職員ごとの上書きで持ち、役職を変えても職員ごとに足した権限を残し、職員の管理と照合も権限で許す](0041-pbac-grants.md)

決定に関わる事実は次のとおり。

- 職員の権限（`user_policies` と `user_policy_targets`）は、職員の登録、権限を足す、権限を外す、役職を変える、チームを変えたときの対象の移し替えの 5 つの操作で変わる。ほかに、役職のデフォルトを変えるマイグレーションが、今いる職員の権限を変える（`000009`、ADR-0041）。役職の作成は、その役職の職員に配る権限を決める。
- 権限の変更の記録は無い。誰がいつ職員の権限を今の形にしたかは、DB からも読めない。
- 運営者が、事業所、標準の役職、最初のマネージャーを登録する、予定の API の運営用のコマンド（CLI）を作ると決めている（#986）。CLI は公開のポートに開かず、web の職員の登録と同じ処理を通る。既に有効なマネージャーがいる事業所にマネージャーを足すのは、明示のフラグを付けたときだけ許す。運営者は職員ではなく、`users` の行を持たない。CLI の実行者は、実行ごとに必須の引数 `--operator` で運営者の ID を渡し、メールと名前は渡さない。
- 予定の削除の監査の記録（`schedule_deletions`）は、削除と同じトランザクションで予定の API の DB に書き、画面に出さない。
  - ADR-0040: [誤って入れた予定を、キャンセルと別の削除で消し、開始の日が今日以降の有効な予定に限り、監査の記録だけを残す](0040-schedule-deletion.md)
- 予定の API には、リクエストの相関 ID が無い。ログは JSON で標準出力に書き、トークン、cookie、利用者の名前を出さない。ログを集める先と保存期間は、インフラのリポジトリが決める。
- 職員と事業所の行は消さない。退職した職員の行も残る。
  - ADR-0004: [職員の停止を、戻せる休職と、戻せない退職に分ける](0004-staff-leave-and-retirement.md)

## Decision

権限を変える操作と運営者の登録の操作を、予定の API の DB の監査の記録（`permission_audits`）に残す。

### 残す操作

| `action` | 操作 | 操作する人 | 対象 |
| --- | --- | --- | --- |
| `facility.create` | 事業所を登録する | 運営者 | 事業所 |
| `position.create` | 役職を作る。運営者の標準の役職の作成を含む | 職員、運営者 | 役職 |
| `staff.create` | 職員を登録し、役職のデフォルトの権限をコピーする。運営者の最初のマネージャーの登録を含む | 職員、運営者 | 職員 |
| `staff.create_forced` | 明示のフラグを付けて、既にマネージャーがいる事業所にマネージャーを登録する。`staff.create` は書かず、この 1 行だけを書く | 運営者 | 職員 |
| `grant.add` | 職員に権限を足す | 職員 | 職員 |
| `grant.remove` | 職員の権限を外す | 職員 | 職員 |
| `position.change` | 職員の役職を変え、権限を置き換える。今と同じ役職に変えたときは権限が変わらないので残さない | 職員 | 職員 |
| `team.change` | 職員のチームを変え、権限の対象を移す。権限の対象が変わらなければ残さない | 職員 | 職員 |
| `grant.migrate` | マイグレーションで職員の権限を変える。役職のデフォルトを今の職員に広げるときを含む | 運営者（マイグレーション） | 職員 |

- 職員の権限が今の形になった操作を、記録だけでたどれるようにするためである。
- フラグを付けた登録だけを別の action にするのは、事業所の外から管理者を足す操作で、乱用を探すときに分けて読むためである。
- 休職、復職、退職は残さない。権限を変えず、職員の状態の記録は ADR-0004 の範囲である。
- 記録は、操作と同じトランザクションで書く。記録を書けなければ操作も失敗するので、記録の無い変更が起きない。失敗した操作（400、403、404、409 を含む）は残さない。
- 運営用の CLI の 1 回の実行は、事業所、役職、職員の操作ごとに 1 行を書き、同じ `request_id` でつなぐ。トランザクションのまとまりは、各操作の処理のまとまりに合わせる。
- #986 が構造化ログに出すと決めた登録の記録は、この記録に移す。
- 職員の権限を変えるマイグレーションは、権限が変わった職員ごとに `grant.migrate` の 1 行を、同じマイグレーションの中で書く。1 つのマイグレーションの行は、同じ `request_id` でつなぐ。記録は、監査のテーブルを作った後のマイグレーションから書き、それより前のマイグレーション（`000009` など）と操作の分はさかのぼって書かない。
- 監査のテーブルを作るマイグレーションは、その時点の全ての職員の権限を、記録の始まりとして 1 人 1 行ずつ書く。`action` は `grant.migrate`、`before` は空、`after` はその時点の権限の全量にする。`actor_operator` は `migration:<そのマイグレーションの番号>` にし、全ての行を 1 つの `request_id` でつなぐ。始まりの行と、その後の記録だけで、今の権限の経緯をたどれるようにするためである。
- マイグレーションの down で権限を戻すときも、権限が変わった職員ごとに `grant.migrate` の 1 行を書く。down でも記録は消さない。

### 記録の中身

| 列 | 内容 | 必須 |
| --- | --- | --- |
| `id` | 記録の ID（ULID） | 必須 |
| `facility_id` | 事業所 | 必須 |
| `action` | 上の表の操作 | 必須 |
| `actor_kind` | 操作した人の種類。`staff` か `operator` | 必須 |
| `actor_user_id` | 操作した職員。`actor_kind` が `staff` のときだけ持つ。`facility_id` との複合の外部キーで、同じ事業所の職員を指す | `staff` のとき必須 |
| `actor_operator` | 操作した運営者（1〜255 文字）。CLI の操作では引数 `--operator` で渡した運営者の ID、マイグレーションでは `migration:<番号>` を入れる。`actor_kind` が `operator` のときだけ持つ | `operator` のとき必須 |
| `target_user_id` | 対象の職員。`staff.*`、`grant.*`、`position.change`、`team.change` で持つ | 操作による |
| `target_position_id` | 対象の役職。`position.create` で持つ | 操作による |
| `before` | 変更の前の権限の全量（JSON） | 操作による |
| `after` | 変更の後の権限の全量（JSON） | 操作による |
| `request_id` | 相関 ID。API はリクエストごとに、CLI は 1 回の実行ごとに振り、ログにも同じ値を書く。マイグレーションは、1 つのマイグレーションの中で 1 つの値を振る | 必須 |
| `occurred_at` | 操作の時刻 | 必須 |

- 操作した人は、種類の列と、職員と運営者の 2 つの列で表す。職員は `users` を外部キーで指せ、運営者は `users` の行を持たないためである。種類と 2 つの列の組は、CHECK 制約でそろえる。
- CLI の操作では、`actor_operator` に運営者の ID を入れ、運営者のメールと名前は入れない。CLI は運営者の ID を、実行ごとに必須の引数 `--operator` で受け取る。ログにも同じ ID を書く。
- マイグレーションは、`actor_kind` を `operator` にし、`actor_operator` を `migration:<番号>`（例: `migration:000024`）にする。マイグレーションは運営者が流すものだからである。CLI は、`migration:` で始まる `--operator` を拒み、運営者の ID とマイグレーションの値が同じにならないようにする。
- `before` と `after` は、差分ではなく全量で持つ。役職の変更では多くの行が一度に変わり、差分では前の状態を組み立て直す必要があるためである。
  - 職員を対象にする操作（`staff.*`、`grant.*`、`position.change`、`team.change`）では、職員の役職とチームの ID と、権限の `code` と対象の職員かチームの ID の並びを持つ。役職を変えたときに残る権限は前の役職のデフォルトで決まり、チームを変えたときは対象が移るので、役職とチームも記録だけで読めるようにする。
  - 役職の作成では、役職の名前とデフォルトの権限の `code` の並びを持つ。
  - 登録と役職の作成の `before` は持たない。`facility.create` は、`facility_id` のほかに対象と `before` と `after` を持たない。
- 職員と利用者の名前とメールは持たない。ログに出さない値の規則に合わせ、職員は ID で指す。

### 見る人と保存期間

- 監査の記録は画面にも API にも出さない。運営者が DB で読む。ADR-0040 の監査の記録と同じ扱いにする。
- 記録は消さず、書き換えない。権限の変更は少なく、消す仕組みが要らないためである。

## Considered Options

### 保存先

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 予定の API の DB に、操作と同じトランザクションで書く | 記録が漏れない。ADR-0040 と同じ形 | テーブルとマイグレーションが増える |
| 構造化ログだけに出す | テーブルが要らない | 保存期間がインフラの設定しだいで、ログが落ちると記録も無い |
| DB とログの両方 | ログの基盤でも検索できる | 書く箇所が 2 つになる |

### 残す操作

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 職員の権限を変える 5 つの操作と、役職の作成と、運営者の登録と、マイグレーションによる職員の権限の変更 | 職員の権限が今の形になった操作を、記録だけでたどれる | 書く操作が多い |
| 権限を足す、外す、役職を変えるの 3 つだけ | 書く箇所が少ない | 登録と役職の作成で付いた権限を、記録からたどれない |
| 上に、休職、復職、退職を足す | 管理者の人数の変化もたどれる | 休職と退職は権限を変えず、職員の状態の記録は別の関心である |

### マイグレーションで変えた権限

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 運営者の操作として記録し、操作した人を `migration:<番号>` にする | 職員の権限の経緯を、記録だけでたどれる | マイグレーションごとに、変更の前後の全量を SQL で組む |
| 記録せず、Git の履歴で追う | マイグレーションの SQL が単純なまま | 職員ごとの権限の経緯を、記録だけではたどれない |
| `actor_kind` に `migration` を足す | 運営者の操作と種類の列で区別できる | 採用の案と同じ手間に加え、種類と CHECK 制約が増える |

### 監査のテーブルを作る前の権限

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** テーブルを作るマイグレーションで、全ての職員の権限を始まりの行として書く | 記録だけで、今の権限の経緯をたどれる | テーブルを作るマイグレーションで、全ての職員の権限の全量を SQL で組む |
| 始まりの行を書かず、その後の変更だけを書く | テーブルを作るマイグレーションが単純になる | 一度も変えていない職員の権限は、記録に出てこない |
| 前のマイグレーションと操作の分も、さかのぼって作る | 過去の経緯も記録で読める | 過去の操作した人と時刻が分からず、作った記録が正しいと言えない |

### 操作した人の表し方

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 種類の列と、職員の列と運営者の列 | 職員を外部キーで指せ、運営者も同じテーブルに残る | 列が 3 つになり、CHECK 制約が要る |
| `staff:<ID>` か `operator:<運営者の ID>` の 1 つの文字列の列 | 列が 1 つ | 職員を外部キーで指せず、退職した職員の行と結び付いているかを DB で確認できない |
| 運営者のテーブルを足し、操作した人を外部キーで指す | 運営者も外部キーで指せる | 運営者の登録と管理の仕組みが要る。運営者は buddy の外にいる |

### 変更の前後の持ち方

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 前と後の全量 | 記録 1 行で、その時点の権限が読める | 行が大きくなる |
| 差分（足した権限と外した権限） | 行が小さい | 前の状態を知るには、記録をさかのぼって組み立てる必要がある |

### 見る人と保存期間

| 論点 | 選択肢 | 強み | 弱み |
| --- | --- | --- | --- |
| 見る人 | **採用:** 画面に出さず、運営者が DB で読む | 画面と API が要らない | 事業所の管理者は、自分で履歴を見られない |
| 見る人 | 職員の管理の権限を持つ職員に、職員の詳細で出す | 事業所の管理者が自分で確認できる | 画面仕様書、API、画面が要る。乱用した管理者も自分の履歴を見られる |
| 保存期間 | **採用:** 消さない | 消す仕組みが要らない | 退職した職員の ID が残り続ける |
| 保存期間 | 決めた年数で消す | 古い記録を持たない | 消す処理と、年数の根拠が要る |

## Consequences

### Positive

- 職員の権限を、いつ、誰が、どの操作で今の形にしたかを、DB の記録で追える。
- 運営者が事業所の外から管理者を作った操作を、職員の操作と分けて読める。
- 記録を書けないときは操作も失敗するので、記録の無い権限の変更が起きない。

### Negative

- 権限を変える全ての操作と、運営用の CLI が、同じトランザクションで記録を書く必要がある。
- 職員の権限を変えるマイグレーションは、変更の前後の全量を SQL で組んで記録を書く必要がある。
- 監査のテーブルを作る前に付いた権限は、始まりの行で今の形だけが分かり、そこに至った操作は記録に無い。
- 予定の API に相関 ID を振る仕組みが要る。
- 事業所の管理者は、記録を画面で見られない。履歴を問われたら、運営者が DB で読む。
- 記録の行は消えないので、件数が増え続ける。
