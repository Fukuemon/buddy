# ADR-0011: 予定の API の DB を PostgreSQL にし、見直したテーブルでマイグレーションを作り直す

## Status

承認

## Context

予定の API の DB は MySQL 8.4 で、sqlc、golang-migrate、MySQL の testcontainers-go のモジュールを使う。テーブルには次の問題がある。

- カラムに照合順序を指定しておらず、MySQL 8.4 のデフォルトの `utf8mb4_0900_ai_ci` が全ての文字列のカラムに適用される。清音と濁音、ひらがなとカタカナ、全角と半角、小書きのかなと普通のかな、大文字と小文字を同じ文字として比べる。部署、チーム、役職の名前の一意の制約が別の名前を拒み、名前の絞り込みがほかの人を返す。テストが使うメモリ上のリポジトリは完全に一致する値だけを同じとみなすので、テストと DB の動きが違う。
- 外部キーは `id` だけを指すので、別の事業所の職員や利用者を指すレコードを DB は通す。今は、全ての書き込みの手順で、アプリが事業所を比べて止めている。
- 予定の種類の規則が、マスタの名前（通常、訪問）に依存する。1 つの訪問の情報を、複数の予定から参照できる。繰り返しの規則のテーブルが事業所を持たない。置き換えた回が、元の何日の回かを持たない。
- Google カレンダーとの同期のために、外部のカレンダー、同期の状態、予定と外部の予定の ID の対応のテーブルが要る。
  - ADR-0009: [Google カレンダーとの連携を、buddy をマスターにする段階の同期にし、サービスアカウントとカレンダーの共有で認証する](0009-google-calendar-sync.md)

予定の API はまだリリースしていない。`main` に予定の API のコードが無く、リリースのタグも無いので、本番の環境に予定の API のデータは無い。検証の環境に残すデータがあるかは確かめていない。マイグレーションは前のバージョンのアプリが動いたまま適用できるものだけにし、`down` で戻さない約束がある。

- 出典: [全体の Design Doc のマイグレーション](../design/DesignDoc.md#マイグレーション)
- 出典: [基盤と運用の Rollback](https://github.com/Fukuemon/buddy/blob/develop/context/operations.md#rollback)

## Decision

予定の API の DB を PostgreSQL 18 にし、見直したテーブルを新しい 1 本の初期のマイグレーションで作り直す。今の 000001〜000010 は消す。データの移し替えはしない。

- 移し替えない理由: 本番の環境に移すべきデータが無い。DB の種類を替えると、前のバージョンのアプリが同じ DB で動き続けられないので、マイグレーションの約束は、この 1 回に当てはまらない。この 1 回だけを例外にし、次のマイグレーションから約束に戻る。
- 検証の環境に残すデータがあれば、切り替える前に書き出し、新しいテーブルに合わせて取り込む。要るかは、切り替える前にインフラの側で確かめる。
- バージョン: 正式に出ている最新の PostgreSQL 18 にする。19 は、2026-10-15 に最初のリリース候補が出た段階である。19 に上げるのは、正式に出た後に、ほかのメジャーバージョンの更新と同じ手順で行う。
  - 出典: [PostgreSQL 19 RC 1 Released!](https://www.postgresql.org/about/news/postgresql-19-rc-1-released-3409/)
- ドライバー: pgx/v5 の `pgxpool` を直接使う。テーブルを見直すとアダプタはほぼ書き直しになるので、`database/sql` で差分を小さくする利点が薄い。
- クエリ: sqlc を `engine: postgresql` で続ける。
-マイグレーションを適用するコマンド: golang-migrate を続け、ドライバーを pgx/v5 に替える。マイグレーションのファイルの埋め込みと、`migrate` のコマンドの使い方が変わらない。
- テストの DB: testcontainers-go の PostgreSQL のモジュールにする。今と同じく、テストが DB のコンテナを立てる。
- 照合順序: デフォルトの決定的な照合順序のまま、名前を完全に一致する値だけで比べる。メールアドレスは、予定の API が小文字にそろえてから保存し、比べる。メモリ上のリポジトリと同じ比べ方になる。
- 型
  - ID は `text COLLATE "C"` にし、主キーだけに ULID の形の CHECK を付ける。API と固定のマスタの ID が ULID の文字列なので、変換が要らない。
  - 監査の時刻は `timestamptz` にし、`updated_at` はトリガーで付ける。
  - 予定の日付と時刻は、事業所の現地の時刻として `date` と `time` で持つ。
  - アプリが値を知っていて属性を持たない区分値は `text` と CHECK にする。属性を持つマスタと、API が ID で返すマスタはテーブルにする。
- テーブルの直し
  - 事業所の中の参照は、`(facility_id, id)` の複合の外部キーで、事業所をまたげないようにする。
  - 予定の種類にコードのカラムを足し、規則はコードで読む。
  - 予定が指す訪問の情報は一意にする。
  - 繰り返しの規則を繰り返しの予定のテーブルに入れ、組み合わせの規則を CHECK で示す。
  - 置き換えた回の予定に、元の回の日付を持たせ、繰り返しの予定と元の日付の組を一意にする。
  - PostgreSQL は外部キーのカラムに index を自動で作らないので、外部キーのカラムの index を明示する。
- Google カレンダーの取り込み（ADR-0009 の段階 1）で使うテーブルを、同じ初期のマイグレーションに入れる。書き出しと双方向の同期のテーブルは、それぞれの段階のマイグレーションで足す。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** PostgreSQL 18 に替え、見直したテーブルを新しい初期のマイグレーションで作り直す | テーブルの直しと DB の移行が 1 回で済む。照合順序の問題がテストと同じ比べ方で解ける |マイグレーションの約束を 1 回だけ例外にする |
| 今の 10 本のマイグレーションを PostgreSQL に訳して移し、テーブルの直しを後のマイグレーションに重ねる |マイグレーションの約束に例外を作らない | 訳したテーブルをすぐに作り直すので、作業が 2 回になる |
| MySQL のまま、テーブルと照合順序だけを直す |マイグレーションを適用するコマンドとドライバーを替えない | カラムごとに照合順序を指定して直すことになり、DB を移す依頼が残る |
| メールに `citext`、名前に大小文字を区別しない ICU の照合順序を使う | DB だけで大小文字を無視して比べられる | メモリ上のリポジトリとの比べ方の差が残る |
| ID を `uuid` にする | index が小さく、比べるのが速い | API と固定のマスタの ID との境界で変換が要り、Go の全ての ID の型が変わる |

## Consequences

### Positive

- 名前の一意の制約と絞り込みが、別の名前を同じとみなさない。テストと DB が同じ比べ方になる。
- 事業所をまたぐ参照を、アプリに加えて DB でも止める。
- Google カレンダーの取り込みのテーブルが、最初から事業所の境界を持つ。

### Negative

- 手で直すファイルが約 40、作り直す生成物が約 40 ある。DB のアダプタ、クエリ、テスト、ローカル環境の起動、CI、テーブル定義書の生成、E2E のシードを 1 つの pull request で替える。途中で分けると、ビルドと CI が通らない。
- インフラの側で、予定の API の DB を PostgreSQL で用意し直す必要がある。環境変数の名前は変えない。
- 検証環境で予定の API を動かし始めた後は、この例外を使えない。
