# ADR-0041: 権限を役職のデフォルトと職員ごとの上書きで持ち、役職を変えても職員ごとに足した権限を残し、職員の管理と照合も権限で許す

## Status

承認

## Context

職員が扱える予定の範囲は、[PRD の役職ごとの権限](../PRD.md#役職ごとの権限)にある 7 つの予定の権限で決まる。

- 同じ役職でも、職員によって見てよい予定が違う。例として、チームに属さない職員の予定を、特定のメンバーにだけ見せる。
- 予定の権限のうち 4 つは、対象の職員かチームを指定する（指定した職員の予定の閲覧など）。
- 管理者は、職員を登録するたびに権限を 1 つずつ選びたくない。
- 権限の context は、判定に役職を直接使わず、職員の権限（`user_policies`）だけを読むと決めている。
- 権限を足し外す操作と役職を変える操作で、職員が自分に権限を足すことを許すと、予定の判定の意味が無くなる。
- 事業所で照合をするのは事務の職員で、事務の職員は訪問せず、照合の食い違いを予定表で直す。
- 職員が buddy で何をしてよいかは予定の API が持ち、ブローカーは権限を持たない。照合の API は、職員を探さずに、トークンの組織だけで事業所を決める。
  - ADR-0001: [認証を OIDC のブローカーと BFF のサーバー側のセッションにし、職員の身元をブローカーが、権限と業務のデータを予定の API が持つ](0001-auth.md)
- web の BFF は、職員の access token を Bearer で付けて、照合の API と予定の API を呼ぶ。1 つの access token の `aud` に、`schedule` と `receipt` の両方が入る。
- ブローカーは、Hydra の `oauth2.token_hook` に 204 か 403 だけを返す。200 を返すと、Hydra は access token の追加のクレームを置き換え、同意で入れた `org_id` が消える。
- 照合の API は、web の BFF を通らずにも呼べる。ドキュメントサイトの API の仕様のページと、手で取ったトークンからも呼べる。
- 予定の API の `GET /v1/me` は、トークンの職員と、その職員の権限を返す。休職と退職の職員には 403 を返す。
- 事業所を作る API は無い。事業所の役職は、運営側が事業所を足すときに作るか、職員の管理の権限を持つ職員が役職の作成の API で作る。
- 役職のデフォルトの権限を変える API は無い。役職は作成と取得だけである。役職のデフォルトを変えたのは、照合の権限を足したマイグレーション（`000009_receipt_check_policy`）だけで、そのときは今いる職員にも権限を足した。
- `user_policies` は、役職のデフォルトからコピーした権限か、職員ごとに足した権限かを持たない。職員の詳細の画面は、職員の今の役職のデフォルトにある権限を「役職で付く権限」、それ以外を「個別に足した権限」として、権限の種類で分けて出す。
- 職員の管理の権限を持つ職員が職員の権限を増やす操作は、権限を足す、役職を変える、デフォルトの権限を付けた役職を作る、職員を登録する、の 4 つである。ほかに、チームを変える操作が、権限の対象を新しいチームに移す。
- 予定の API は、リクエストごとに職員と `user_policies` を読み、権限をキャッシュしない。web は画面を読み込むたびに `GET /v1/me` を読み、照合の API は照合のたびに `GET /v1/me` を呼ぶ。

## Decision

### 権限の持ち方

権限を `policies` のレコードとして持ち、職員ごとに付ける（PBAC）。役職は、職員に付ける権限のデフォルトだけを持つ。

- `policies` は 9 つの権限を持つ。7 つの予定の権限、職員の管理（`staff.manage`）、照合（`receipt.check`）である。`position_policies` は、役職ごとのデフォルトの権限を持つ。
- 職員を登録したときに、予定の API は役職のデフォルトの権限を `user_policies` にコピーする。
- 職員の管理の権限を持つ職員は、その後に職員の `user_policies` を足し、外せる。認可は `user_policies` だけを読む。
- 対象を指定する権限は、`user_policy_targets` に対象の職員かチームを持つ。役職のデフォルトの権限からコピーするときは、チームの対象を職員の所属のチームにする。

認可の評価を `user_policies` の 1 か所にすると、職員の権限の一覧が DB のレコードのまま画面に出せる。

### 役職を変えたとき

役職を変えたときは、変える時点の前の役職のデフォルトにある権限を対象ごと消し、新しい役職のデフォルトの権限をコピーする。前の役職のデフォルトに無い権限（職員ごとに足した権限）は、対象ごと残す。  
役職を変えても、管理者が職員ごとに足した権限が意図せず消えないようにするためである。

- 職員ごとに足した権限かは、列で持たず、前の役職のデフォルトにあるかで決める。画面のまとまりと同じ決め方で、画面に「個別に足した権限」と出た権限が、役職を変えた後にも残る。
  - 列を足すと、今ある行を 2 つに分けるマイグレーションが要り、分ける根拠も同じ比べ方しか無いためである。
- 前の役職のデフォルトにある権限は、職員ごとに対象を直していても、役職の権限として消す。画面のまとまりも、対象ではなく権限で決めている。
- 職員ごとに足した権限が、新しい役職のデフォルトにもあるときは、今の行と対象を残し、デフォルトからコピーしない。同じ職員に同じ権限は 1 つだけ付くので、どちらかを選ぶ必要があり、職員ごとに選んだ対象の方が新しい判断だからである。
- 事業所で職員の管理の権限を持つ最後の有効な職員かは、変更の後の権限で判定する。職員ごとに足した `staff.manage` が残るなら、`staff.manage` を持たない役職にも変えられる。

### 役職のデフォルトを変えるとき

役職のデフォルトの権限を変える操作は作らない。デフォルトを変えるときは、マイグレーションで、その役職の今いる職員の `user_policies` にも明示して広げる。

- デフォルトを変えるのは、PRD の仮決定のデフォルトを直すときで、稀である。`000009` と同じく、変える人がマイグレーションで今の職員の扱いを決める。
- 事業所の管理者が別のデフォルトを使いたいときは、役職を作って職員の役職を変える。

### 権限の変更を判定に使う時期

権限の変更は、次のリクエストから判定に使われる。予定の API と照合の API は、変更を待たずに、次のリクエストで変わった権限で拒む。  
web で開いたままの画面は、次に読み込むまで前の権限で出し分ける。拒むのは API なので、出し分けが古くても権限の外の操作は通らない。

### 職員の管理の権限

職員の管理（`staff.manage`）は、対象を指定しない権限（`needs_target` が false）で、マネージャーの役職のデフォルトの権限にする。  
職員と利用者の登録、役職の作成、職員の権限を足し外す操作、役職を変える操作は、この権限を持つ職員だけに許す。  
役職の作成を含めるのは、役職にデフォルトの権限を付けると、その役職の職員に権限を配れるためである。

- 役職ではなく権限で判定するので、権限の context の禁止に合う。
- 予定の権限とは範囲が違うので、7 つの予定の権限の判定の規則は変えない。
- 職員の管理の権限を持つ職員は、自分を含む職員に任意の権限を足せるので、事実上の最上位の権限である。自分への付与は止めない。

職員の管理の権限で配れる権限に上限を設けない。自分の権限を足し外す操作と、自分の役職を変える操作も止めない。  
権限の変更は、監査の記録で後から追う。

- 上限を設けても、職員の管理の権限を持つ職員は、デフォルトの権限を付けた役職を作り、自分かほかの職員に付けられる。上限は、権限を増やす 4 つの操作の全てで確認しないと、上限にならない。
- 管理者が 1 人の事業所では、自分の権限を自分で直せないと、運営側が DB を直すことになる。
- 自分に権限を足すことを止めないので、Context の「予定の判定の意味が無くなる」おそれは、職員の管理の権限を持つ職員に限って残る。職員の管理の権限を配る相手を絞り、監査の記録で後から追うことで扱う。
- 監査の記録は、次の ADR で決めた。
  - ADR-0042: [権限の変更を、操作した職員か運営者と変更の前後の権限の全量で、予定の API の DB の監査の記録に残す](0042-permission-audit.md)

職員の管理の権限は 1 つのままにし、職員の管理と権限の管理に分けない。運営者は、web と予定の公開の API の外から、事業所を足す手順で操作する。運営者の操作も監査の記録に残る（ADR-0042）。

職員の管理の権限を持つ職員（操作する職員）が行う権限の操作は、次のとおり許す。拒むときの列は、権限に関わる拒否だけを挙げ、入力の誤りとメールの重なりのような拒否は挙げない。

| 操作 | 自分に | ほかの職員に | 拒むとき |
| --- | --- | --- | --- |
| 任意の権限（`staff.manage` を含む）を足す | 許す | 許す | 同じ権限が既にある。対象が別の事業所のもの |
| 権限を外す | 許す | 許す。ほかの管理者からも外せる | 外すと、事業所で `staff.manage` を持つ有効な職員がいなくなる |
| 役職を変える | 許す | 許す。ほかの管理者の役職も変えられる | 変更の後の権限で、事業所で `staff.manage` を持つ有効な職員がいなくなる |
| チームを変え、権限の対象を新しいチームに移す | 許す | 許す | — |
| デフォルトの権限を付けた役職を作る | — | — | 同じ名前の役職がある |
| 役職を付けて職員を登録する | — | 許す | 役職が別の事業所のもの |
| 休職と退職にする | 拒む | 許す | 自分を対象にする。事業所で `staff.manage` を持つ有効な職員がいなくなる（ADR-0004） |

職員の管理の権限を持たない職員は、どの操作も 403 で拒まれる。判定は予定の API で行い、画面の出し分けを境界にしない。

### 照合の権限

照合（`receipt.check`）は、対象を指定しない権限（`needs_target` が false）である。照合の API の照合（`POST /v1/checks`）は、予定の CSV で照合するときも対象の月で照合するときも、この権限を持つ職員だけに許す。

- 照合の API は、受けた access token をそのまま付けて予定の API の `GET /v1/me` を呼び、返った権限に照合があるかで判定する。無ければ 403 を返す。予定の API が 401 か 403 を返したときも 403 を返す。
  - 理由: 権限を持つのは予定の API である（ADR-0001）。トークンにクレームとして入れると、ブローカーが権限を読むことになり、ログインが予定の API に依存する。BFF だけで確認すると、BFF を通らない呼び出しを拒めない。
  - 照合は月に数回の操作なので、照合のたびに予定の API を 1 回呼んでも負荷は問題にならない。
- 照合の画面と照合の結果の画面は、照合の権限を持つ職員にだけ出す。web は `GET /v1/me` の権限で出し分け、拒むのは照合の API である。
- 照合の権限は、職員の管理の権限を持つ職員が、ほかの職員にも職員ごとに足せる。

### 標準の役職とデフォルトの権限

標準の役職は、マネージャー、チームリーダー、メンバー、事務の 4 つである。標準の役職は、事業所を足すときに作る役職で、名前は事業所ごとに変えてよい。判定は役職を使わないので、名前を変えても判定は変わらない。

役職のデフォルトの権限のうち、事務の役職と違いがあるものは、次のとおり。

| 権限 | マネージャー | チームリーダー | メンバー | 事務 |
| --- | --- | --- | --- | --- |
| 自分の予定の編集 | あり | あり | あり | なし |
| 事業所の全ての予定の閲覧 | あり | なし | なし | あり |
| 事業所の全ての予定の編集 | あり | なし | なし | あり |
| 照合 | あり | なし | なし | あり |

- 事務の役職に、事業所の全ての予定の閲覧と編集を付ける。照合の食い違いを予定表で直すためである。
- 事務の役職に、自分の予定の編集を付けない。訪問しない職員は予定を持たないためである。
  - ADR-0006: [訪問するかを職員に持ち、訪問しない職員を予定と担当から外す](0006-non-visiting-staff.md)
- 表にない権限（指定した職員と、指定したチームの職員の予定の閲覧と編集、職員の管理）の各役職のデフォルトは、PRD の役職ごとの権限の表のとおりで、事務の役職には付けない。

## Considered Options

### 権限の持ち方

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 役職のデフォルトの権限を職員にコピーし、職員ごとに上書きする | 評価が 1 か所で、職員の権限がそのまま読める。対象の職員とチームを指定できる | 役職のデフォルトを変えても、今いる職員の権限は変わらない |
| 役職だけで権限を決める（RBAC） | テーブルが少なく、評価が簡単 | 「指定した職員」を表せない。例外ごとに役職を増やすことになる |
| 役職のデフォルトの権限をコピーせず、評価のたびに役職のデフォルトの権限と職員ごとの差分（許可と拒否）を合成する | 役職を変えても職員ごとの差分が残る | 評価と画面の表示の両方で合成が要り、拒否と許可の優先の規則を決める必要がある |
| 汎用のポリシーエンジン（OPA、Casbin など）に規則を書く | 属性による複雑な規則を書ける | この数の権限には過剰で、規則がアプリの外の言語に分かれる |

### 役職を変えたときの、職員ごとに足した権限

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 前の役職のデフォルトに無い権限を、職員ごとに足した権限として残す | 職員ごとに足した権限が意図せず消えない。評価は `user_policies` の 1 か所のまま。列を足さず、今あるデータを移さない | 前の役職のデフォルトにある権限の対象を職員ごとに直していても、役職の権限として置き換わる |
| 職員の権限と対象を全て消し、新しい役職のデフォルトをコピーし直す | 役職を変えると、権限が新しい役職のデフォルトにそろう | 職員ごとに足した権限が消える。画面の注意を読まずに変えると、元の権限を覚えていないと戻せない |
| `user_policies` に、デフォルトからコピーしたか職員ごとに足したかの列を足し、職員ごとの行を残す | 対象を職員ごとに直した権限も区別できる | 今ある行をどちらかに分けるマイグレーションが要り、分ける根拠は採用の案と同じ比べ方しか無い |
| デフォルトと職員ごとの許可と拒否を、評価のたびに合成する | 役職を変えても、デフォルトを変えても、差分が残る | 権限の持ち方の表と同じ弱みに加え、保存の形と判定を作り直し、今あるデータを移す |

### 役職のデフォルトを変えるとき

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** デフォルトを変える操作を作らず、変えるときはマイグレーションで今いる職員にも広げる | API と画面が増えない。変える人が、今いる職員の扱いを毎回決める | 事業所の管理者は、デフォルトを自分で直せない |
| デフォルトを変える API を作り、その役職の今いる職員に同じトランザクションで広げる | 役職を直すと、全員の権限がそろう | 外した権限を全員が一度に失う。最後の管理者の判定も要る |
| デフォルトを変える API を作り、今いる職員には広げない | 今いる職員の権限が急に変わらない | 同じ役職で、今いる職員と新しい職員の権限が違う |
| デフォルトを変える API を作り、広げるかを管理者が選ぶ | 管理者が影響を見て決められる | 広げる処理と広げない処理の両方と、確認の画面が要る |

### 職員の管理を許す職員

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 職員の管理の権限を足す | 判定が `user_policies` だけを読むまま、マネージャー以外にも職員ごとに許せる | 権限が増え、PRD の表とデフォルトの権限を直す |
| 役職がマネージャーの職員に許す | 表を変えない | 判定に役職を使い、権限の context の禁止に反する。役職の名前は事業所ごとに違う |
| 事業所の全ての予定の編集の権限を持つ職員に許す | 権限を足さない | 予定の権限を、職員の管理という別の範囲に流用する |
| 事業所の職員なら誰でも許す | 判定が要らない | 職員が自分に全ての権限を足せる |

### 職員の管理の権限で配れる範囲

| 論点 | 選択肢 | 強み | 弱み |
| --- | --- | --- | --- |
| 配れる権限の上限 | **採用:** 上限を設けず、監査の記録で後から追う | 画面と API を変えない。少人数の事業所で、管理者が自分で直せる | 管理者の誤りと乱用を、事前には止めない |
| 配れる権限の上限 | 操作する職員が持つ権限の範囲までにする | 自分に無い権限を配れない | 権限を増やす 4 つの操作の全てで確認する必要があり、対象を持つ権限の「範囲内」の比べ方も決める必要がある |
| 自分への操作 | **採用:** 止めない。最後の有効な管理者の保護だけを残す | 管理者が 1 人の事業所でも、自分の権限を直せる | 自分で自分の権限を増やせる |
| 自分への操作 | 自分に権限を足す操作と、自分の役職を変える操作を拒む | 自分の権限を増やすには、ほかの管理者が要る | 管理者が 1 人の事業所では運営側が直すことになる。役職を作って付ける道が残る |
| 自分への操作 | 自分の権限と役職の変更を全て拒む | 規則が単純 | 自分の不要な権限も外せない |
| 権限の分け方 | **採用:** 職員の管理の権限を 1 つのままにし、運営者を buddy の外に置く | 変更が無い | 職員の登録だけを任せる職員を作れない |
| 権限の分け方 | 職員の管理と権限の管理に分ける | 権限を配れる職員を絞れる | 権限が 10 になり、PRD、画面、マイグレーションを直す |
| 権限の分け方 | 事業所をまたぐ運営者の権限を buddy の中に作る | 運営側が画面で事業所を直せる | 事業所の分離の規則の例外になる |

### 照合と事務の役職

| 論点 | 選択肢 | 強み | 弱み |
| --- | --- | --- | --- |
| 照合の判定 | **採用:** 照合の API が、受けたトークンで予定の API の `GET /v1/me` を呼ぶ | 権限を予定の API だけが持つまま、照合の API で拒める。権限を外すと次の照合から拒む | 照合の API が予定の API に依存し、予定の API が止まると照合できない |
| 照合の判定 | ブローカーが token_hook で権限をトークンのクレームに入れる | 照合の API が外部を呼ばない | ブローカーが権限を読み、ログインが予定の API に依存する（ADR-0001 で採らなかった案）。権限を外しても、トークンを取り直すまで照合できる |
| 照合の判定 | web の BFF だけで確認する | 照合の API を変えない | BFF を通らない呼び出しを拒めない |
| 照合の判定 | 予定の API に照合の権限の確認だけの API を足す | 返す内容が少ない | `GET /v1/me` で足りる判定のために API が増える |
| 事務の役職 | **採用:** 4 つ目の標準の役職 | 事業所を足すときに、照合の担当にすぐ役職を付けられる | 標準の役職とデフォルトの権限の表が大きくなる |
| 事務の役職 | 標準にせず、事業所が役職の作成で作る | 標準の役職を変えない | 事業所ごとに、照合と全ての予定の権限を付けた役職を作る手順が要る |

## Consequences

### Positive

- 職員ごとの例外を、役職を増やさずに表せる。
- 認可は `user_policies` と `user_policy_targets` を読むだけで決まる。
- 役職を変えても、職員ごとに足した権限が残る。
- 職員の管理を、役職によらず職員ごとに与えられる。
- 照合と照合の結果を、照合の権限を持つ職員だけが扱える。BFF を通らない呼び出しも拒める。照合の権限を外すと、その職員の次の照合から拒む。

### Negative

- 役職を変えると、前の役職のデフォルトにある権限は、職員ごとに対象を直していても新しい役職のデフォルトに置き換わる。画面は、役職を変える前に、置き換わる権限と残る権限を管理者に示す必要がある。
- 役職のデフォルトの権限を変えても、既にいる職員の `user_policies` は変わらない。デフォルトを変えるマイグレーションは、今いる職員の権限も明示して変える必要がある。
- 職員の管理の権限を持つ職員の誤りと乱用は、事前には止めず、監査の記録で後から追う。
- 事業所で職員の管理の権限を持つ最後の有効な職員が、それを失うと、その事業所で権限を足し外せる職員がいなくなり、DB を直すほかに戻せない。このため予定の API は、その職員から権限を外す操作と、変更の後に職員の管理の権限が残らない役職の変更を 409 で拒む。権限を外したい管理者は、先にほかの職員に職員の管理の権限を足す必要がある。
  - 休職と退職も、同じ規則で拒む。
    - ADR-0004: [職員の停止を、戻せる休職と、戻せない退職に分ける](0004-staff-leave-and-retirement.md)
- 照合の API が予定の API に依存する。予定の API が止まっていると、予定の CSV での照合もできない。照合の API の起動の設定に、予定の API の URL が要る。
- 照合の権限を持つ職員は、事業所の全ての利用者の名前を含む実績と照合の結果を扱える。照合の権限を足すときに、職員の管理の権限を持つ職員がそれを知っておく必要がある。
