# ADR-0014: 照合を照合の権限で許し、事務の役職を足し、訪問しない職員を予定と担当から外す

## Status

承認

## Context

照合は、事業所の全ての職員が使える。PRD は照合の担当を役職を問わないとし、照合の API は権限を確認しない。役職は、マネージャー、チームリーダー、メンバーの 3 つである。  
事業所で照合をするのは事務の職員で、事務の職員は訪問しない。事務の職員は、照合の食い違いを予定表で直す。

この ADR は、ADR-0002 と ADR-0006 の判断を補う。権限の持ち方と、判定が職員の権限（`user_policies`）だけを読む規則は変えない。

- ADR-0002: [権限を役職のデフォルトと職員ごとの上書きで持つ（PBAC）](0002-pbac.md)
- ADR-0006: [職員と利用者の登録と、職員の権限と役職を変える操作を、職員の管理の権限で許す](0006-staff-manage-policy.md)

決定に関わる事実は次のとおり。

- ADR-0001 は、職員が buddy で何をしてよいかを予定の API が持ち、ブローカーは権限を持たないと決めた。照合の API は、職員を探さずに、トークンの組織だけで事業所を決める。
  - ADR-0001: [認証を OIDC のブローカーと BFF のサーバー側のセッションにし、職員の身元と停止をブローカーが、権限と業務のデータを予定の API が持つ](0001-auth.md)
- web の BFF は、職員の access token を Bearer で付けて、照合の API と予定の API を呼ぶ。1 つの access token の `aud` に、`schedule` と `receipt` の両方が入る。
- ブローカーは、Hydra の `oauth2.token_hook` に 204 か 403 だけを返す。200 を返すと、Hydra は access token の追加のクレームを置き換え、同意で入れた `org_id` が消える。
- 照合の API は、web の BFF を通らずにも呼べる。ドキュメントサイトの API の仕様のページと、手で取ったトークンからも呼べる。
- 予定の API の `GET /v1/me` は、トークンの職員と、その職員の権限を返す。休職と退職の職員には 403 を返す。
- 予定のカレンダーの職員の列、予定者の候補、利用者の担当の候補は、有効な職員を全て出す。事務の職員も出る。
- 事業所を作る API は無い。事業所の役職は、運営側が事業所を足すときに作るか、職員の管理の権限を持つ職員が役職の作成の API で作る。

## Decision

### 照合の権限

9 つ目の権限として、照合（`receipt.check`）を `policies` に足す。対象を指定しない権限（`needs_target` が false）である。照合の API の照合（`POST /v1/checks`）は、予定の CSV で照合するときも対象の月で照合するときも、この権限を持つ職員だけに許す。

- 照合の API は、受けた access token をそのまま付けて予定の API の `GET /v1/me` を呼び、返った権限に照合があるかで判定する。無ければ 403 を返す。予定の API が 401 か 403 を返したときも 403 を返す。
  - 理由: 権限を持つのは予定の API である（ADR-0001）。トークンにクレームとして入れると、ブローカーが権限を読むことになり、ログインが予定の API に依存する。BFF だけで確認すると、BFF を通らない呼び出しを拒めない。
  - 照合は月に数回の操作なので、照合のたびに予定の API を 1 回呼んでも負荷は問題にならない。
- 照合の画面と照合の結果の画面は、照合の権限を持つ職員にだけ出す。web は `GET /v1/me` の権限で出し分け、拒むのは照合の API である。

### 事務の役職

事務の役職を、マネージャー、チームリーダー、メンバーと並ぶ 4 つ目の標準の役職にする。標準の役職は、事業所を足すときに作る役職で、名前は事業所ごとに変えてよい。判定は役職を使わないので、名前を変えても判定は変わらない。

役職のデフォルトの権限は、次のとおり。

| 権限 | マネージャー | チームリーダー | メンバー | 事務 |
| --- | --- | --- | --- | --- |
| 自分の予定の編集 | あり | あり | あり | なし |
| 事業所の全ての予定の閲覧 | あり | なし | なし | あり |
| 事業所の全ての予定の編集 | あり | なし | なし | あり |
| 照合 | あり | なし | なし | あり |

- 事務の役職に、事業所の全ての予定の閲覧と編集を付ける。照合の食い違いを予定表で直すためである。
- 事務の役職に、自分の予定の編集を付けない。訪問しない職員は予定を持たないためである。
- 照合の権限は、職員の管理の権限を持つ職員が、ほかの職員にも職員ごとに足せる。
- 表にない権限（指定した職員と、指定したチームの職員の予定の閲覧と編集、職員の管理）の各役職のデフォルトは、PRD の役職ごとの権限の表のとおりで、事務の役職には付けない。

### 訪問しない職員

職員に「訪問するか」を持たせる。役職には持たせない。職員を登録するときの初期値は「訪問する」で、職員の管理の権限を持つ職員が変える。

- 理由: 役職のデフォルトにすると、役職を変える操作が、予定と担当の扱いを変える操作を兼ねる。役職を変える操作は、今は権限だけをコピーし直す。
- 訪問しない職員は、予定のカレンダーの職員の列と絞り込みに出さず、予定の職員、主訪問者、同行者、利用者の担当の候補に出さない。
- 予定の API は、訪問しない職員への新しい割り振り（予定の作成、職員の変更、主訪問者と同行者の変更、利用者の担当の変更）を拒む。休職と退職の職員への割り振りを拒む規則と同じ形にする。
  - 理由: カレンダーに列が出ないので、訪問しない職員に予定を持たせても、誰からも見えない。
- 「訪問する」から「訪問しない」へ変えるときは、その日以降の予定、繰り返しの予定、担当の利用者を一覧で返し、一覧が空になるまで拒む。一覧の範囲は、退職の確認と同じである。
  - 理由: 誰も行かない訪問を残さないためである。
  - ADR-0001: [認証を OIDC のブローカーと BFF のサーバー側のセッションにし、職員の身元と停止をブローカーが、権限と業務のデータを予定の API が持つ](0001-auth.md)
- 過去の予定は、職員を変えずに残す。過去の予定と照合の結果で、誰が訪問したかを読めるようにする。
- 「訪問しない」から「訪問する」へは、確認なしで変えられる。

## Considered Options

| 論点 | 選択肢 | 強み | 弱み |
| --- | --- | --- | --- |
| 照合の判定 | **採用:** 照合の API が、受けたトークンで予定の API の `GET /v1/me` を呼ぶ | 権限を予定の API だけが持つまま、照合の API で拒める。権限を外すと次の照合から拒む | 照合の API が予定の API に依存し、予定の API が止まると照合できない |
| 照合の判定 | ブローカーが token_hook で権限をトークンのクレームに入れる | 照合の API が外部を呼ばない | ブローカーが権限を読み、ログインが予定の API に依存する（ADR-0001 で採らなかった案）。権限を外しても、トークンを取り直すまで照合できる |
| 照合の判定 | web の BFF だけで確認する | 照合の API を変えない | BFF を通らない呼び出しを拒めない |
| 照合の判定 | 予定の API に照合の権限の確認だけの API を足す | 返す内容が少ない | `GET /v1/me` で足りる判定のために API が増える |
| 事務の役職 | **採用:** 4 つ目の標準の役職 | 事業所を足すときに、照合の担当にすぐ役職を付けられる | 標準の役職とデフォルトの権限の表が大きくなる |
| 事務の役職 | 標準にせず、事業所が役職の作成で作る | 標準の役職を変えない | 事業所ごとに、照合と全ての予定の権限を付けた役職を作る手順が要る |
| 訪問するか | **採用:** 職員に持つ | 役職を変えずに、訪問するかだけを変えられる | 職員を登録するたびに選ぶ。事務の職員を登録するときに変え忘れると、候補に出る |
| 訪問するか | 役職に持つ | 役職を付ければ決まる | 役職の変更が予定と担当の扱いを兼ね、同じ役職で訪問する職員としない職員を分けられない |
| 訪問しない職員の予定 | **採用:** 予定の職員にも指せない | カレンダーに出ない予定が生まれない | 事務の職員が、会議などの通常の予定を buddy で持てない |
| 訪問しない職員の予定 | 通常の予定だけ持てる | 事務の職員が自分の予定を入れられる | カレンダーに列が出ないので、入れた予定が見えない |
| 訪問しないへの変更 | **採用:** 残る予定と担当があれば拒む | 誰も行かない訪問が残らない | 変える前に割り振り直す手順が要る |
| 訪問しないへの変更 | 拒まずに警告を返す | 操作が 1 回で済む | 列が出ない職員の予定が残り、気付けない |

## Consequences

### Positive

- 照合と照合の結果を、照合の権限を持つ職員だけが扱える。BFF を通らない呼び出しも拒める。
- 照合の権限を外すと、その職員の次の照合から拒む。
- 事務の職員が、予定のカレンダーの列と、予定と担当の候補に出ない。

### Negative

- 照合の API が予定の API に依存する。予定の API が止まっていると、予定の CSV での照合もできない。照合の API の起動の設定に、予定の API の URL が要る。
- 事務の職員は、会議などの通常の予定を buddy で持てない。
- 照合の権限を持つ職員は、事業所の全ての利用者の名前を含む実績と照合の結果を扱える。照合の権限を足すときに、職員の管理の権限を持つ職員がそれを知っておく必要がある。
- 役職のデフォルトの権限を変えても、既にいる職員の権限は変わらない（ADR-0002 の Negative）。照合の権限を足すまで、職員の管理の権限を持たない職員は照合できなくなる。
  - #376 で、今いる職員の扱いを補った。マイグレーションで、職員の管理の権限を持つ今いる職員に照合の権限を足す。理由は [権限の Design Doc の権限のレコード](https://github.com/Fukuemon/buddy/blob/develop/services/schedule/internal/access/DesignDoc.md#権限のレコード) にある。
- 事務の職員を登録するときに「訪問しない」に変え忘れると、カレンダーの列と候補に出る。
