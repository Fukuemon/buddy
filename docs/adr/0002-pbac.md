# ADR-0002: 権限を役職のデフォルトと職員ごとの上書きで持つ（PBAC）

## Status

承認

## Context

職員が扱える予定の範囲は、[PRD の役職ごとの権限](../PRD.md#役職ごとの権限)にある 7 つの権限で決まる。

- 同じ役職でも、職員によって見てよい予定が違う。例として、チームに属さない職員の予定を、特定のメンバーにだけ見せる。
- 権限のうち 4 つは、対象の職員かチームを指定する（指定した職員の予定の閲覧など）。
- 管理者は、職員を登録するたびに 7 つの権限を 1 つずつ選びたくない。

## Decision

権限を `policies` のレコードとして持ち、職員ごとに付ける（PBAC）。役職は、職員に付ける権限のデフォルトだけを持つ。

- `policies` は 7 つの権限を持つ。`position_policies` は、役職ごとのデフォルトの権限を持つ。
  - この判断は ADR-0006 で補った。`policies` に職員の管理（`staff.manage`）を足し、権限は 8 つになった。
  - ADR-0006: [職員と利用者の登録と、職員の権限と役職を変える操作を、職員の管理の権限で許す](0006-staff-manage-policy.md)
- 職員を登録したときと役職を変えたときに、schedule-api は役職のデフォルトの権限を `user_policies` にコピーする。役職を変えたときは、職員の `user_policies` を消し、新しい役職のデフォルトの権限をコピーし直す。
- 管理者は、その後に職員の `user_policies` を足し、外せる。認可は `user_policies` だけを読む。
  - この判断は ADR-0006 で補った。権限を足し外せる管理者は、職員の管理の権限を持つ職員である。
  - ADR-0006: [職員と利用者の登録と、職員の権限と役職を変える操作を、職員の管理の権限で許す](0006-staff-manage-policy.md)
- 対象を指定する権限は、`user_policy_targets` に対象の職員かチームを持つ。役職のデフォルトの権限からコピーするときは、チームの対象を職員の所属のチームにする。

認可の評価を `user_policies` の 1 か所にすると、職員の権限の一覧が DB のレコードのまま画面に出せる。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 役職のデフォルトの権限を職員にコピーし、職員ごとに上書きする | 評価が 1 か所で、職員の権限がそのまま読める。対象の職員とチームを指定できる | 役職を変えると、職員ごとに足した権限が消える |
| 役職だけで権限を決める（RBAC） | テーブルが少なく、評価が簡単 | 「指定した職員」を表せない。例外ごとに役職を増やすことになる |
| 役職のデフォルトの権限をコピーせず、評価のたびに役職のデフォルトの権限と職員ごとの差分（許可と拒否）を合成する | 役職を変えても職員ごとの差分が残る | 評価と画面の表示の両方で合成が要り、拒否と許可の優先の規則を決める必要がある |
| 汎用のポリシーエンジン（OPA、Casbin など）に規則を書く | 属性による複雑な規則を書ける | 7 つの権限には過剰で、規則がアプリの外の言語に分かれる |

## Consequences

### Positive

- 職員ごとの例外を、役職を増やさずに表せる。
- 認可は `user_policies` と `user_policy_targets` を読むだけで決まる。

### Negative

- 役職を変えると、管理者が足した権限が消える。画面は、役職を変える前に、消える権限を管理者に示す必要がある。
- 役職のデフォルトの権限を変えても、既にいる職員の `user_policies` は変わらない。既にいる職員に適用するには、役職を付け直す操作が要る。
