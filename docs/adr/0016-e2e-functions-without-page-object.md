# ADR-0016: E2E のテストのコードを、Page Object を使わず page を受け取る関数で書き、描画の完了の信号をアプリに足さない

## Status

承認

## Context

E2E のテストのコード（`packages/e2e/`）で、画面の操作と待ちをどこに書くかを決める。  
この判断は、E2E のテストのコードの Design Doc の「設計の背景」に書いていた。  
Design Doc は検討した選択肢を持たないので、判断と理由をこの ADR に移す。

決定に関わる事実は次のとおり。

- E2E のテストは Playwright で書く。Playwright の locator は、操作と確認のたびに要素が出るのを自動で待つ。
- テストのコードは、spec、`screens/`、`widgets/`、`selectors/` の層に分ける。層と依存の向きは、[E2E のテストのコードの設計の層と依存の向き](https://github.com/Fukuemon/buddy/blob/develop/packages/e2e/DesignDoc.md#層と依存の向き) にある。
- 描画のライブラリを置き換える改修では、改修の前と後で同じ E2E のテストを流し、振る舞いが同じことを示す。

## Decision

テスト用のクラスは作らず、`page` を引数に取る関数を並べる。  
locator は spec に書き、`screens/` には共有する「開く、モードを変える」だけを置く。  
Page Object は、要素の取得と待ちを自前で書くための書き方だった。  
locator が自動の待ちを持つ Playwright では、要素を 1 つのオブジェクトに集める利点が小さい。

観点ごとの違いは次のとおり。

| 観点 | Page Object | page を取る関数 |
| --- | --- | --- |
| 共有の粒度 | クラスの全体。1 本の spec しか使わないメソッドも、同じクラスに入る | export した関数 1 つずつ。3 本以上が使うものだけを置き、残りは spec に書ける |
| 依存の見え方 | spec はクラスを import する。どのメソッドを使うかは、中を読まないと分からない | spec の import の行に、使う名前だけが並ぶ |
| 待ちの責任 | 曖昧になりやすい | 操作する関数が、中で待ち切る。呼ぶ側は待ちを書かない |
| 失敗したときに読む場所 | spec、クラス、継承元 | spec、`screens/`、`widgets/`、`selectors/` の最大 3 段 |

描画の完了をアプリに出させる案（`data-render-state` などの属性を足す）は採らない。  
アプリのコードに手を入れると、描画のライブラリを置き換える改修で、改修の前と後が同じ振る舞いだと示せなくなる。  
待ちは、テストの側で観測できるもの（API のレスポンス、ライブラリが作る DOM）で組み立てる。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** `page` を受け取る関数と、テストの側で観測できるものでの待ち | 使う関数だけを import し、失敗したときに読む場所が最大 3 段に収まる。アプリのコードに手を入れない | 共有する関数を、使う spec の数で `screens/` に置くか spec に書くかを決める必要がある |
| Page Object | 画面ごとの操作を 1 つのクラスに集められる | 1 本の spec しか使わないメソッドもクラスに入り、どのメソッドを使うかが中を読まないと分からない。待ちの責任が曖昧になりやすい |
| アプリに描画の完了の属性を足す | テストが 1 つの属性を待てばよい | 描画のライブラリを置き換える改修で、改修の前と後が同じ振る舞いだと示せなくなる |

## Consequences

### Positive

- spec の import の行を読めば、spec が使う共有の関数が分かる。
- 描画のライブラリを置き換える改修でも、同じ E2E のテストで前と後を比べられる。

### Negative

- 待ちを、API のレスポンスやライブラリが作る DOM から組み立てる必要がある。
