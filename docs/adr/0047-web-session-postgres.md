# ADR-0047: web のセッションを、web 用の PostgreSQL のデータベースに暗号化して置けるようにし、期限の切れた行を web が消す

## Status

承認

## Context

web のセッションの保存先を、Valkey のほかに PostgreSQL からも選べるようにする必要がある。本番環境で、セッションのための保存先を別に用意せずに済むようにするためである。

- web のセッションには、access token、refresh token、ID token と、職員の ID、名前、事業所、権限の有無が入る。cookie にはセッションの ID だけを入れる。
  - ADR-0001: [認証を OIDC のブローカーと BFF のサーバー側のセッションにし、職員の身元をブローカーが、権限と業務のデータを予定の API が持つ](0001-auth.md)
- refresh token の期限は、Hydra のデフォルトの 720 時間である。セッションは 12 時間で切れる。
- web は、セッションの読み書きを `SessionStore` のインターフェースで行う。refresh を 1 本にするための鍵（`lock` と `unlock`）も同じインターフェースにある。
- 検証環境と本番環境では、Hydra、ブローカー、予定の API のデータベースを同じ PostgreSQL のインスタンスに置き、アプリごとにロールを分ける。同じインスタンスでは、管理者の権限とインスタンスのバックアップが、全てのアプリのデータに届く（[基盤と運用の Databases](https://github.com/Fukuemon/buddy/blob/develop/context/operations.md#databases)）。
- 本番環境の PostgreSQL は、接続の数の上限が小さい構成を見込む。予定の API、ブローカー、Hydra は、それぞれ接続のプールを持つ。
- 2026-11-11 に利用者が、利用する人数が多くないので、セッションを DB に置く案でよいと判断した。同じ日に利用者が、セッションを置くデータベース、暗号化、テーブルを作る方法、期限の切れた行の扱い、設定の渡し方、負荷の検証の条件を、下の Decision のとおりに決めた（#1032）。

## Decision

### 保存先の選び方と接続

- `SESSION_STORE_URL` のスキームで保存先を選ぶ。`redis://` なら Valkey、`postgres://` か `postgresql://` なら PostgreSQL に置く。
  - 理由: Valkey の環境は、設定を変えずに今までどおり動く。
- PostgreSQL のとき、web のインスタンスごとの接続の数の上限を `SESSION_STORE_MAX_CONNS`（デフォルト 5）で渡す。使っていない接続は 30 秒で閉じる。
  - 理由: 接続の数の上限が小さい PostgreSQL で、web のインスタンスが増えても、ほかのアプリの接続を奪わない。
- `sslmode` は URL のクエリで渡す。URL にパスワードが入るので、PostgreSQL のときの `SESSION_STORE_URL` はシークレットとして扱う。
- 接続のプーラーを transaction のモードで通しても動くよう、セッションの読み書きでは、名前付きの prepared statement と advisory lock を使わない。

### データベースとロール

- web 用のデータベースとロールを新しく作り、web のロールだけが CONNECT できるようにする。ほかのアプリと同じく、[基盤と運用の Databases](https://github.com/Fukuemon/buddy/blob/develop/context/operations.md#databases) の規則に従う。
  - 理由: 予定の API とブローカーの資格が漏れても、トークンの行を読めない。
- ローカル環境の compose は、ほかのアプリと同じく 1 つのロールで、データベース `web` につなぐ。

### テーブル

- 値は `web_sessions`（`key`、`value`、`expires_at`）に、鍵は `web_session_locks`（`key`、`token`、`expires_at`）に置く。
- 時刻は、全て DB の `now()` で比べる。
  - 理由: web のインスタンスの時計の差で、期限の判定が変わらない。
- 読むときは、`expires_at > now()` で絞る。期限の切れた行は、消す前から読まれない。
- 鍵は、期限の切れた行だけを 1 つの文で奪い、放すときは自分のトークンの行だけを消す。Valkey の `SET NX PX` と、トークンを比べて消すスクリプトと同じ動きにする。

### 暗号化

- 値は、web が AES-256-GCM で暗号化して置く。鍵は `SESSION_SECRET` から HKDF で導き、新しいシークレットを足さない。key を追加の認証データに入れる。
  - 理由: DB の管理者の権限とバックアップから、有効な refresh token が平文で読めない。行の値を別の key に写しても復号できない。
- `SESSION_SECRET` を替えると、置いた値は全て読めなくなり、全ての職員のログインが切れる。cookie の署名も同じ値で検証するので、替えたときに切れる範囲は今と変わらない。
- Valkey の保存先は、今までどおり暗号化しない。

### テーブルを作る方法

- web のイメージに `/usr/local/bin/migrate` を足す。`migrate up` は、`SESSION_STORE_URL` の PostgreSQL に、まだ当てていない版を当てて終わる。
- インフラは、予定の API とブローカーと同じく、新しいイメージを起動する前に、同じイメージで `migrate up` を 1 回流す。
  - 理由: デプロイの要件の形が、アプリの間でそろう。
- `migrate` は、版を二重に当てないよう advisory lock を取る。プーラーを通さず、直に PostgreSQL につなぐ。

### 期限の切れた行の扱い

- web のプロセスが、10 分ごとに、期限の切れた行を、テーブルごとに 1 回 1000 行まで消す。
  - 理由: インフラのジョブが増えない。複数のインスタンスで同時に流しても、同じ行を消すだけで、結果は 1 回のときと同じになる。
- 消すのに失敗したら、警告のログ（`session purge failed`）を書き、次の回に試し直す。
- インスタンスが 0 台の間は消えない。その間はセッションの行も増えない。

### 負荷の検証

- 想定の利用の量は、事業所 5、同時にログインしている職員 100 人とし、その 3 倍（300 人）でも流す。
  - 職員 1 人が平均 2 秒に 1 回、web の BFF を呼ぶ。
  - 職員ごとに 5 分に 1 回、トークンを更新する。
  - 全員が 5 分の間にログインする。
- 合否の基準は、次の 3 つにする。
  - セッションの読み取りの p95 が 10 ms 以下
  - 接続の数が、DB の接続の数の上限の 80% 以下
  - DB の CPU が 50% 以下
- ローカルの compose の PostgreSQL に CPU、メモリ、接続の数の上限を付けて流す。後から、k6 のようなツールで、ローカルと検証環境で流し直す（#1040）。2026-11-11 に利用者が決めた。
- 条件と結果は、[#1032 の負荷の検証の結果](../verification/1032-session-store-load/README.md) にある。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** web 用のデータベースとロールを作る | ほかのアプリの資格でトークンを読めない。DB の規則にそのまま合う | データベース、ロール、シークレットが 1 つずつ増える |
| ブローカーのデータベースに置く | データベースが増えない | ブローカーのデータベースに、web のテーブルとロールが入る |
| 予定の API のデータベースに置く | データベースが増えない | 業務のデータとトークンが同じデータベースに入る |
| **採用:** `SESSION_SECRET` から導いた鍵で暗号化する | DB の管理者とバックアップから平文で読めない。シークレットが増えない | `SESSION_SECRET` を替えると全員のログインが切れる |
| 別のシークレットの鍵の一覧で暗号化する | cookie の署名の鍵と別に替えられる | シークレットと、鍵を替える手順が増える |
| 暗号化しない | 実装が最も小さい | DB の管理者とバックアップを読める人に、有効な refresh token が見える |
| **採用:** web のイメージに `migrate up` を足す | デプロイの要件の形がそろう | web のデプロイの手順が 1 つ増える |
| web が起動のときにテーブルを作る | インフラの手順が増えない | テーブルの形を変えるときに、仕組みを作り直すことになる |
| **採用:** web のプロセスが定期に消す | インフラのジョブが増えない | リクエストを受けるプロセスに処理が増える |
| 掃除のコマンドをジョブで 1 日 1 回流す | リクエストを受けるプロセスに処理を足さない | ジョブとスケジューラーが増える |
| DB の側の定期の仕組みで消す | アプリに処理を足さない | ローカルの compose の PostgreSQL に無く、環境ごとに有無が違う |
| **採用:** `SESSION_STORE_URL` のスキームで選ぶ | 環境変数が 1 つ増えるだけで、Valkey の環境は変わらない | PostgreSQL のとき、URL がシークレットになる |
| 保存先の名前と `DB_*` の環境変数で選ぶ | パスワードの名前がほかのアプリとそろう | web の環境変数が 6 つ増える |

## Consequences

### Positive

- 本番環境と検証環境で、セッションのための保存先を別に用意せずに済む。
- DB の管理者とバックアップから、トークンが平文で読めない。
- Valkey の保存先は、設定を変えずにそのまま使える。

### Negative

- セッションの読み書きの負荷が、ほかのアプリと同じ PostgreSQL のインスタンスにかかる。
- web の接続のプールの分だけ、DB の接続の数を使う。インスタンスの数に `SESSION_STORE_MAX_CONNS` を掛けた数を、接続の数の上限の見積もりに足す。
- web のデプロイに、`migrate up` の手順が増える。
