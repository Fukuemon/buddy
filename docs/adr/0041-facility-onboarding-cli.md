# ADR-0041: 事業所と最初のマネージャーを予定の API の運営用の CLI で登録し、ブローカーは運営用のクライアントに職員の登録だけを許す

## Status

提案

## Context

運営者が事業所を足すときに、事業所、標準の役職、最初のマネージャーを登録する手段が要る。

- 事業所を作る API は無い。事業所の役職は、運営側が事業所を足すときに作る。
  - ADR-0007: [権限を役職のデフォルトと職員ごとの上書きで持ち、職員の管理と照合も権限で許す](0007-pbac.md)
- 職員の登録は、職員の管理の権限（`staff.manage`）を持つ職員だけが web で行える。事業所の最初の 1 人を登録する手段が無い。
- 職員の管理の権限を持つ職員は、自分に任意の権限を足せるので、事実上の最上位の権限である。最初のマネージャーのメールを誤ると、別の人が事業所の全てのデータを扱える。
  - ADR-0007: [権限を役職のデフォルトと職員ごとの上書きで持ち、職員の管理と照合も権限で許す](0007-pbac.md)
- 職員の登録は、ブローカーと予定の API の DB の 2 か所に書く。ブローカーの職員を登録の途中の状態で作り、予定の API に書いてから有効にする。登録の途中の職員はログインできない。
  - ADR-0001: [認証を OIDC のブローカーと BFF のサーバー側のセッションにし、職員の身元をブローカーが、権限と業務のデータを予定の API が持つ](0001-auth.md)
- ブローカーの内部の API は、Hydra の client credentials の access token を受け、許したクライアントに全ての操作（登録、有効化、削除、休職、復職、退職）を許す。内部のポートは、ブラウザとリバースプロキシに開かない。
  - ADR-0002: [OIDC のブローカーを、Ory Hydra と、自作の login and consent app で作る](0002-id-broker-hydra.md)
- 事業所ごとの上流の IdP の設定（組織の ID）は、インフラからファイルでブローカーに渡す。ブローカーは、設定に無い組織の職員の登録を 400 で拒む。
  - ADR-0002: [OIDC のブローカーを、Ory Hydra と、自作の login and consent app で作る](0002-id-broker-hydra.md)
- 職員の登録には、部署、チーム、役職が要る。
- 新しい事業所の予定の正本のデフォルトは、Google カレンダー（`google_primary`）である。
  - ADR-0029: [Google カレンダーとの連携を、事業所ごとの正本のモードで分ける](0029-google-calendar-sync.md)
- 本番のマイグレーションは、インフラのリポジトリが内部のネットワークの 1 回のジョブとして流す。

## Decision

### 登録の手段

予定の API のイメージに運営用の CLI（`ops`）を入れ、マイグレーションと同じく内部のネットワークの 1 回のジョブとして流す。公開のポート（web、Hydra の public API、ブローカーのログインの画面）に、事業所や管理者を作る API を足さない。

- `ops onboard-facility` は、1 つの DB のトランザクションの中で、事業所、標準の 4 つの役職とデフォルトの権限、最初のマネージャーの部署とチームを、無ければ作る。続けて、web からの職員の登録と同じ処理で、マネージャーの役職の職員を登録する。
  - 理由: 職員の登録を同じ処理にすると、ブローカーと予定の API の 2 か所の書き込みの順と戻し方が、web と同じになる。役職のデフォルトの権限のコピーを誤らない。
- ブローカーの有効化は、トランザクションのコミットの前に行う。ブローカーへの登録か有効化が失敗すると、事業所を含む予定の API の書き込みを全て戻す。上流の IdP の設定に無い組織の ID は、ブローカーへの登録の失敗になるので、何も書かずに失敗する。
  - ブローカーに残った登録の途中の職員はログインできず、同じ引数で流し直すと同じ職員として登録し直す。
  - コミットだけが失敗すると、ブローカーの職員が有効のまま予定の API に職員が無い。予定の API はトークンの職員を引けないので、その職員は buddy を使えない。同じ引数で流し直すと、予定の API に書く。
- 同じ組織の ID の事業所があれば、事業所と役職を作らずに使う。名前が違えば、名前を変えずに失敗する。部署とチームは、同じ名前があれば使う。
- 同じメールの職員が、職員の管理の権限を持つ有効な職員として事業所にいれば、何も書かずに成功する。同じ引数での流し直しが、重ならずに終わる。
- 職員の管理の権限を持つ有効な職員が事業所に既にいれば、マネージャーを足すのを拒む。明示のフラグ（`--allow-additional-manager`）を付けたときだけ許す。
  - 理由: 運営者が事業所の外から管理者を作る操作を、全てのマネージャーが退職したときの復旧に限る。
- 書き込まずに内容を表示するモード（`--dry-run`）は、同じ手順をトランザクションの中で行ってから戻し、ブローカーを呼ばない。
- 新しい事業所の予定の正本は、新しい事業所のデフォルト（`google_primary`）にする。

### ブローカーの運営用のクライアント

Hydra に運営用のクライアント（`schedule-ops`）を足し、ブローカーは、そのクライアントに、内部の API のうち職員の登録、有効化、登録の途中の職員の削除だけを許す。休職、復職、退職は 403 で拒む。

- 理由: 運営用のクライアントだけを止められ、ブローカーのログでも予定の API の呼び出しと区別できる。漏れても、既にいる職員を止める操作には使えない。
- 予定の API のクライアントと運営用のクライアントは、ブローカーの設定の別の値（`INTERNAL_API_CLIENTS` と `INTERNAL_API_ONBOARDING_CLIENTS`）で許し、同じ ID を両方に入れると起動しない。

### 登録の記録

CLI は、登録の記録を構造化ログ（JSON）で標準出力に書く。

- 記録は、実行者、操作の種類（`facility.onboard`）、事業所と職員の ID、作ったもの、日時、実行ごとの相関の ID を持つ。
- メールと職員の名前は書かない。エラーの文に入ったメールは伏せる。
- 実行者は、必須の引数 `--operator` の運営者の ID で表す。ID は英数字と `.`、`_`、`-` の 64 文字までに限り、メールと名前を記録に入れない。

## Considered Options

| 論点 | 選択肢 | 強み | 弱み |
| --- | --- | --- | --- |
| 登録の手段 | **採用:** 予定の API の運営用の CLI を、内部のネットワークの 1 回のジョブとして流す | 公開のポートから管理者を作れない。web と同じ職員の登録の処理を通せる | 運営者は、ジョブを流せる権限と、DB と運営用のクライアントの secret を持つ |
| 登録の手段 | 予定の API に運営者用の HTTP の API を足す | 運営者がジョブを用意せずに呼べる | 公開のポートから、事業所の全てのデータを扱える管理者を作れる |
| 登録の手段 | 本番の DB に手で SQL を流す | 仕組みが要らない | 予定の API とブローカーの 2 つの DB が食い違い、役職のデフォルトの権限のコピーを誤りやすい |
| ブローカーの資格 | **採用:** 運営用のクライアントを分け、職員の登録の操作だけを許す | 運営用のクライアントだけを止められ、ログで区別できる。漏れても休職と退職に使えない | Hydra のクライアントと secret が 1 つ増える |
| ブローカーの資格 | 予定の API と同じクライアントを使う | 設定が増えない | CLI の secret で全ての職員の休職と退職ができる。ログで予定の API と区別できない |
| マネージャーの追加 | **採用:** 有効なマネージャーがいれば、明示のフラグが無ければ拒む | 誤って事業所の外から管理者を足すことを防ぎ、全てのマネージャーが退職したときに戻せる | 復旧のときにフラグを付ける手順が要る |
| マネージャーの追加 | 常に許す | 手順が簡単 | 運営者が事業所の外から管理者をいつでも作れる |
| マネージャーの追加 | 常に拒む | 運営者が管理者を作れない | 全てのマネージャーが退職すると、DB を直すほかに戻せない |
| 登録の記録 | **採用:** 構造化ログに出す | 監査の仕組みを待たずに残せる | ログの保存の期間と検索は、ログの基盤による |
| 登録の記録 | 予定の API の DB に監査のテーブルを作る | DB の変更と同じトランザクションで残せる | 権限の変更の監査と形を合わせずに作ると、2 つの監査の形ができる |

## Consequences

### Positive

- 運営者は、本番の DB に手で SQL を流さずに、事業所と最初のマネージャーを 1 回で登録できる。
- ブローカーへの書き込みが失敗しても、予定の API に事業所と職員が残らない。
- 運営用のクライアントの secret が漏れても、既にいる職員を休職と退職にできない。

### Negative

- インフラのリポジトリに、CLI を流すジョブと、運営用のクライアントの secret の配置が要る。
- 登録の記録は、ログの基盤の保存の期間までしか残らない。権限の変更の監査の仕組みができたら、そちらに移す。
- 運営用のクライアントは、ブローカーの有効化を任意の職員の ID で呼べる。有効化は登録の途中の職員だけを有効にし、休職と退職の職員は 409 で拒むので、止めた職員を戻すことには使えない。
