# #1032 PostgreSQL のセッションの保存先の負荷の検証

[#1032](https://github.com/Fukuemon/buddy/issues/1032) の受け入れ条件の、負荷の検証の条件と結果。  
保存先を PostgreSQL にする判断と合否の基準は、[ADR-0047](../../adr/0047-web-session-postgres.md) にある。

## 結果

想定の利用（同時 100 人）と、その 3 倍（同時 300 人）の両方で、3 つの基準を満たした。

| 基準 | 合格の値 | 100 人 | 300 人 |
| --- | --- | --- | --- |
| セッションの読み取りの p95 | 10 ms 以下 | 4.57 ms | 4.07 ms |
| DB の接続の数の最大 | 上限 25 の 80%（20）以下 | 7 | 10 |
| DB の CPU の最大 | 50% 以下 | 8.62% | 11.12% |

- どちらの回も、読み書きの失敗は 0 件だった。
- 300 人の回で接続の数が 10 に止まったのは、web のインスタンス 2 台が、それぞれ上限 5 の接続のプールを使い切ったためである。人数を増やしても、接続の数は `SESSION_STORE_MAX_CONNS` とインスタンスの数で決まる。

## 測った環境

- 測ったコミットは `bc602b94` である。
- PostgreSQL は `postgres:18.6` のコンテナで、CPU を 1 つ分、メモリを 1 GiB、`max_connections` を 25 に制限した。
  - 接続の数の上限が小さい PostgreSQL を想定した値である。
  - CPU の値は `docker stats` の値で、CPU 1 つ分を 100% とする。
- 負荷を作るスクリプトは、同じ機械（macOS、Docker Desktop）から、web の `SessionStore` の実装を直接呼んだ。
  - スクリプトは `apps/web/scripts/session-load.ts` である。
  - DB への往復は、Docker Desktop のポートの転送を通る。検証環境と本番環境の往復の時間は測っていない。
- web のインスタンスは 2 台とし、それぞれ接続の数の上限を 5 にした（`SESSION_STORE_MAX_CONNS` のデフォルト）。
- DB の接続の数は、5 秒ごとに `pg_stat_activity` で数えた。測るための接続は数えていない。

## 流した利用

| 項目 | 値 |
| --- | --- |
| 同時にログインしている職員 | 100 人と 300 人 |
| 流した時間 | 420 秒 |
| ログイン | 最初の 300 秒に、全員が等しい間隔でログインする。ログインの途中の値を置いて取り出し、セッションを置く |
| 画面の操作 | ログインした職員が、平均 2 秒（1〜3 秒）に 1 回、セッションを読む |
| トークンの更新 | ログインから 300 秒ごとに、鍵を取り、セッションを読み、置き換え、鍵を放す |
| ログアウト | 420 秒で、全員のセッションを消す |

- セッションの値は、トークンの長さを JWT に合わせた、web のセッションと同じ形の値にした。
- 全員がログインし終えるまで、読み取りの回数は少ない。そのため、100 人の回の読み取りは 420 秒で 13550 回（毎秒約 32 回）で、全員がそろった後の毎秒 50 回より少ない。
- トークンの更新は、ログインから 300 秒が過ぎた職員だけが行い、100 人の回で 41 回、300 人の回で 122 回だった。

## 操作ごとの時間

単位はミリ秒。

| 操作 | 人数 | 回数 | p50 | p95 | p99 |
| --- | --- | --- | --- | --- | --- |
| 読み取り | 100 | 13550 | 2.02 | 4.57 | 10.37 |
| 読み取り | 300 | 40718 | 1.87 | 4.07 | 9.75 |
| ログイン | 100 | 100 | 8.52 | 14.90 | 28.73 |
| ログイン | 300 | 300 | 7.75 | 13.65 | 31.63 |
| トークンの更新 | 100 | 41 | 9.20 | 16.03 | 31.54 |
| トークンの更新 | 300 | 122 | 8.25 | 15.14 | 28.45 |
| ログアウト | 100 | 100 | 3.47 | 5.42 | 25.96 |
| ログアウト | 300 | 300 | 2.58 | 5.64 | 12.67 |

- ログインは 3 回、トークンの更新は 4 回の DB の往復を、1 回として測った。

## 流し方

```sh
docker run -d --name session-load-pg --cpus 1 --memory 1g \
  -e POSTGRES_DB=web -e POSTGRES_USER=buddy -e POSTGRES_PASSWORD=buddy-dev \
  -p 127.0.0.1:25434:5432 postgres:18.6 -c max_connections=25
export SESSION_STORE_URL=postgres://buddy:buddy-dev@127.0.0.1:25434/web
node apps/web/migrate/migrate.ts up
LOAD_USERS=100 LOAD_DB_CONTAINER=session-load-pg node apps/web/scripts/session-load.ts
LOAD_USERS=300 LOAD_DB_CONTAINER=session-load-pg node apps/web/scripts/session-load.ts
```

- 結果は、1 行の JSON で標準出力に出る。
- 回の間に `TRUNCATE web_sessions, web_session_locks` で行を消した。
- 人数、インスタンスの数、間隔は、環境変数で変えられる。一覧はスクリプトの先頭にある。

## 残っていること

- k6 のようなツールで、ローカルと検証環境で負荷の検証を流し直す（#1040）。ネットワークの往復の時間と、ほかのアプリと同じインスタンスを使うときの影響を測るためである。
  - ローカルの compose の回は、[#1040 の web の負荷の検証の結果](../1040-web-load/README.md) にある。
