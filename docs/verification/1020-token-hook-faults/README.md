# #1020 token_hook とブローカーの故障を入れる測定を、繰り返せる形にした後の結果

[#877](https://github.com/Fukuemon/buddy/issues/877) で使い捨てで行った故障の測定を、`packages/e2e/faults/` に入れ、1 つのコマンドで流した結果。  
流し方と故障の入れ方は、[基盤と運用](../../../context/operations.md) の「故障を入れる仕組み」にある。  
#877 の後に入った変更（BFF の refresh を 1 度にする、ブローカーの DB の待ちの上限、Hydra が止まっても API が起動する）に合わせて、比べる元を項目ごとに分けた。

## 測った環境

- 測ったコミットは `b77f6b41` である。1 つのコマンドの通しを 2 回と、項目ごとに 1 回流し、秒は 3 回の幅に収まる値で書いた。Ory Hydra は v26.2.0 で、設定は `compose/hydra/hydra.yml` に、hook の宛先だけを環境変数でスタブに向けた。
- compose は、ルートの `compose.yml` の全体に `packages/e2e/faults/compose.faults.yml` を重ねた。
- トークンのエンドポイントは、portless の https の URL で、Playwright の request で直に呼んだ。答えない hook の項目だけは、compose の中の web のコンテナからも呼んだ。
- web の BFF は、ブラウザと同じ道でログインし、Valkey のセッションの `expiresAt` を過ぎた時刻に書き換えて、refresh を起こした。

## 比べる元

| 比べる元 | 当てる項目 |
| --- | --- |
| [#877 の測った結果](../877-token-hook-failures/README.md) | Hydra の層の値。hook を呼ぶ回数、失敗が決まるまでの秒、トークンの要求の結果、refresh token と認可コードを使い切らないこと、既発行の JWT、止めた職員 |
| [ADR-0044](../../adr/0044-token-hook-fail-closed.md) と [基盤と運用](../../../context/operations.md) の Login and Token Failures | #877 の後に変えた動き。web の BFF の見え方とログ、ブローカーの DB の待ちの上限、Hydra が止まっている間の API の起動 |
| 記録だけ | 結果の見込みが立たなかった 2 つ。hook の 501 と、BFF が切った後の Hydra の呼び直し |

## 結果の要約

- #877 と比べた Hydra の層の値は、全て合った。
  - hook の 500 と、つながらないときは、3 回呼んで約 3 秒で 500 `server_error` になる。403 は 1 回で、すぐ `access_denied` になる。
  - 答えない hook は、30 秒を 3 回待ち、約 93 秒で答えを返さずに接続を切る。
  - 故障の間に失敗した refresh token と認可コードは、戻した後にそのまま使えた。
  - 止めた職員は、休職の操作で `invalid_grant`、ブローカーの DB の状態だけを変えたときは hook の `access_denied` で拒まれた。
- ADR-0044 と比べた動きも、全て合った。
  - web は、1 回の表示で refresh を 1 度だけ試し、一時的に使えない画面を出して、セッションを残す。戻した後は、ログインし直さずに画面が出る。
  - ブローカーの DB が答えないときは、hook が 2 秒で打ち切り、約 9 秒で失敗が決まる。web は 5 秒で切る。
  - Hydra が止まっている間に再起動した予定の API は、`/readyz` と、トークンの付いたリクエストに 503 を返し、Hydra のヘルスチェックが通ってから 2〜3 秒で 200 になった。
- 記録だけの 2 つの結果は、次のとおり。
  - hook が 501 を返すと、Hydra は呼び直さない。すぐ返せば 0.1 秒未満、2 秒待って返せば約 2 秒で、クライアントには 500 `server_error` が返る。
  - BFF が 5 秒で切ると、Hydra は途中の hook の呼び出しを切り、残りの呼び直しをしない。

## 故障ごとの結果

どの故障でも、故障の前にログインして取った access token と refresh token を使った。  
「戻した後」は、故障の間に送った refresh token を、故障を戻してから送り直した結果である。

| 故障 | refresh | 新しいログイン | 既発行の JWT で予定の API | client credentials | 戻した後 |
| --- | --- | --- | --- | --- | --- |
| hook の 500 | 約 3 秒で 500 `server_error`。hook は 3 回 | 認可コードの交換が約 3 秒で 500 | 200 | 約 3 秒で 500 | refresh は 200。失敗した認可コードも交換できた |
| hook の 403 | すぐ 403 `access_denied`。hook は 1 回 | 認可コードの交換が 403 | 200 | 403 | refresh は 200 |
| hook の 501 | すぐ 500 `server_error`。hook は 1 回 | 測っていない | 測っていない | 測っていない | refresh は 200 |
| hook が答えない | 約 93 秒で答えが無いまま切れる。hook は 3 回、各 30 秒 | 測っていない | 測っていない | 測っていない | refresh は 200 |
| ブローカーの停止 | 約 3 秒で 500 `server_error`。hook は 3 回 | ブローカーのログインの画面に届かない（502） | 200 | 約 3 秒で 500 | refresh は 200 |
| ブローカーの DB の停止（接続を拒む） | 約 3 秒で 500 `server_error`。ブローカーは 3 回とも 500 | メールを送ると 500 | 測っていない | 200 | refresh は 200 |
| ブローカーの DB が答えない | 約 9 秒で 500 `server_error`。hook は 3 回、各 2 秒 | 測っていない | 測っていない | 測っていない | refresh は 200 |
| Hydra の停止 | 届かない（portless の 502） | 測っていない | 200 | 測っていない | refresh は 200 |
| Hydra の DB の停止 | 401 `invalid_client` | ブローカーのログインの画面にメールを送ると 404 | 200 | 401 `invalid_client` | refresh は 200 |

- ブローカーの停止では、スタブはブローカーに届かず 502 を返す。#877 は、スタブも止めて Hydra から宛先の名前を引けなくした。どちらも Hydra が呼び直す失敗で、回数と秒は同じだった。
- ブローカーの DB が答えない故障は、別の接続でブローカーの `staff` のテーブルを排他のロックで握って入れた。ブローカーのログの `token_hook の結果` の `failed` の `duration_ms` は、どれも 2000〜2011 だった。
- Hydra の DB の停止は、#877 では測っていない。#877 の PostgreSQL の全体の停止と同じく、Hydra は refresh と client credentials に `invalid_client` を返した。
  - 新しいログインは、Hydra の認可のエンドポイントがブローカーのログインの画面へリダイレクトし、メールを送るとブローカーが 404 を返した。ブローカーが Hydra のログインの要求を読めなかったためと推測する。未確認である。

## web の BFF での見え方

access token が切れた職員が、故障の間に予定のカレンダーを開いたときの結果である。

| 故障 | 出た画面 | 出るまで | セッション | web のログの `session refresh failed` | 戻した後 |
| --- | --- | --- | --- | --- | --- |
| hook の 500 | 一時的に使えない画面 | 約 3 秒 | 残る | `reason=hydra_error`、`error=server_error`、`status=500` | ログインし直さずに出た |
| hook の 403 | ログインの失敗の画面（`/auth/error`） | 0.1 秒 | 消える | `reason=rejected`、`error=access_denied` | 測っていない |
| hook が 2.5 秒待って 500 | 一時的に使えない画面 | 約 5 秒 | 残る | `reason=timeout` | ログインし直さずに出た |
| ブローカーの停止 | 一時的に使えない画面 | 約 3 秒 | 残る | `reason=hydra_error`、`error=server_error`、`status=500` | ログインし直さずに出た |
| ブローカーの DB が答えない | 一時的に使えない画面 | 約 5 秒 | 残る | `reason=timeout` | ログインし直さずに出た |
| Hydra の停止 | 一時的に使えない画面 | 0.1 秒 | 残る | `reason=unreachable` | ログインし直さずに出た |
| Hydra の DB の停止 | 一時的に使えない画面 | 0.1 秒 | 残る | `reason=hydra_error`、`error=invalid_client`、`status=401` | ログインし直さずに出た |

- #877 では、access token が切れた職員の 1 回の表示に 7〜27 秒かかり、500 のエラーの画面が出た。BFF が refresh を 1 度だけ試すようになり、Hydra を待つ上限の 5 秒以内に一時的に使えない画面が出る。
- Hydra の DB の停止の `invalid_client` は、セッションを消す値に入っていないので、セッションが残った。

## hook の 501

ブローカーが hook の失敗に 500 ではなく 501 を返したときの動きを、スタブで測った。

| hook の答え | Hydra が hook を呼んだ回数 | refresh の結果 |
| --- | --- | --- |
| すぐ 501 | 1 回 | 0.1 秒未満で 500 `server_error` |
| 2 秒待って 501 | 1 回 | 約 2 秒で 500 `server_error` |
| すぐ 500（参考） | 3 回 | 約 3 秒で 500 `server_error` |

- Hydra は、501 を呼び直さない失敗として扱う。クライアントに返る値は、500 のときと同じである。
- ADR-0044 は、hook の失敗に 500 を返すと決めている。この測定では変えていない。

## BFF が切った後の Hydra の呼び直し

スタブが 2.5 秒待ってから 500 を返す形で、web の access token を切らして予定のカレンダーを開いた。  
Hydra が呼び直しを止めなければ、3 回目の hook が約 8 秒に届く。

| hook | 受けた秒 | 答えた秒 | Hydra が切った秒 |
| --- | --- | --- | --- |
| 1 回目 | 0.1 | 2.6（500） | なし |
| 2 回目 | 3.6 | なし | 5.1 |
| 3 回目 | 届かない | | |

- 秒は、表示を開いてからの時間である。
- BFF が 5 秒で接続を切ると、Hydra は 2 回目の hook の呼び出しを切り、3 回目を呼ばなかった。トークンも発行しない。
- ブローカーの DB が答えない故障でも、web の表示のときにブローカーのログに出た `failed` は 2 行で、3 行目は出なかった。

## 答えない hook のときにクライアントに返るもの

- compose の中の web のコンテナから Hydra を直に呼ぶと、約 93 秒で答えが無いまま接続が切れた（`UND_ERR_SOCKET`）。#877 と同じである。
- portless の https の URL で呼ぶと、portless が切れた接続を 502 `bad_gateway` にして返した。

## 未確認のこと

- Hydra の DB の停止で、ブローカーのログインの画面が 404 を返した理由。
- 本番の構成（Hydra とブローカーの台数、DB のインスタンスの分け方、ロードバランサーの待ちの上限）での動き。ローカル環境の compose は 1 台ずつで、DB は 1 つのインスタンスである。
- hook の 501 での web の見え方。Hydra がクライアントに返す値は 500 のときと同じなので、同じ見え方になると推測する。
