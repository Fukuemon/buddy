# write-e2e-test

E2E のテストのコードを、落ちにくく、直す場所が 1 か所で済む形で書くための判断。  
機械で判定できる規則は、`packages/e2e/eslint/e2e-authoring-rule.mjs` の ESLint の規則が止める。ここには、規則で判定できない判断だけを書く。  
層、配置先、待ち方、禁止する書き方の理由と図は、`packages/e2e/DesignDoc.md` にある。

## 始める前に読むもの

- `context/conventions.md` の E2E の節。testid の命名、固定の待ちを許すファイル、画面 ID の形が書いてある。食い違うときは、context に従う
- `context/testing.md` の E2E の節。流すコマンド、project、環境
- 同じ画面を触る、既にある spec を 1 本

## 層

層ごとの持つものと持たないものは、`packages/e2e/DesignDoc.md` の「層と依存の向き」の表にある。  
書く前にその表を読む。

- `expect` は `specs/` と `setup/` だけに書く。
- `specs/<dir>/` の spec 以外のファイルは値だけを持ち、画面の操作を書かない。
- `widgets/` は、使う spec が 1 本でも置く。中を `actions/` と `waits/` に分け、`actions/` から `waits/` の向きにだけ依存する。testid の接頭辞は引数で受ける。

依存は上の層から下の層へ張る。  
間の層は飛ばしてよく、spec から `widgets/` や `selectors/` を直に呼べる。  
下の層から上の層は呼ばない。  
`fixtures/` と `packages/e2e/kit/` は、どの層から使ってもよい。  
ログインと録画は、`packages/e2e/kit/` の `auth` と `recording` を使い、spec に書き直さない。

## どこに書くか

| 問い | はい | いいえ |
| --- | --- | --- |
| 拾う要素はアプリが描くか | testid を付けて `getByTestId` で拾う | `selectors/` に指し方を置き、そこから呼ぶ |
| 操作の完了は要素や文字に出るか | 待ちを書かず、`expect` の自動の待ちに任せる | `widgets/` の操作を呼ぶ。無ければ、操作と待ちを `widgets/` に足す |
| 同じ「開く、モードを変える」を 3 本目の spec が要るか | `screens/` に移して 3 本から呼ぶ | spec に書く |

- `screens/` に移すかは、3 本目が要った時点で 1 回だけ判断する。数えるのは export ごとにする。
- 複数の画面をまたぐ手順は、spec に書く。
- DOM に完了が出る共通の UI(表、日付の選択)は `widgets/` にせず、spec から testid で操作する。

## 名前

- `specs/` の下のディレクトリは、機能の名前にする。アクター、検証の観点、issue の番号、変更の向き(新しい挙動、移した後)の名前は使わない。
- ファイルは、機能の中の振る舞いで切る。同じ振る舞いを複数の画面で確かめるなら 1 つのファイルにまとめる。
- `describe` は、外側を画面、内側を機能の 2 段にする。アクターの違いは、機能の中の `describe` で表す。
- テストの名前は「{条件}の場合、{期待}であること」にする。観点の ID と規約の ID は、名前にもコメントにも書かない。
- 手動検証のエビデンスの spec の配置先と名前は、`context/testing/evidence.md` にある。決まっていなければ、利用者に尋ねる。

## 待ち方

固定の秒数で待たない。何が終わったかを条件にする。  
完了が要素か文字に出るなら、待ちを書かずに `expect` に任せる。  
出ないときは、`packages/e2e/DesignDoc.md` の「待ち方」の 6 種類から選ぶ。

- 通信が 2 つある画面では、両方のレスポンスを待つ。
- 値を読んでから比べない。locator をそのまま `expect` に渡す。
  - 規則が止めるのは一部の読み方だけ(`packages/e2e/eslint/e2e-authoring-rule.mjs`)なので、`count()` と `isVisible()` も自分で避ける。
  - リクエストの中身や URL のように、locator で表せない値は、読んでから比べてよい。

## 確かめ方

- 「起きないこと」は、`expect.poll` で変わらないことを待って確かめない。後に起きる別の実際の出来事を待ってから、回数や状態を確かめる。
- ラジオは、選び直すと前の選択が外れることまで確かめる。複数選択は、選んだ値がリクエストに全部載ることを確かめる。
- 既にあるテストから操作の列をコピーするときは、その操作が初期値に対して何をするかを先に確かめる。レスポンスが条件によらず同じなら、リクエストの中身を確かめる。
- 共通のコンポーネントに渡した testid で入力の値を確かめるときは、testid を起点に中の `input` か `select` に辿る。`select` の「空であること」は値で確かめる。

次の場面では、[references/situations.md](references/situations.md) の該当の節を読む。

- 新しいタブを開く画面を確かめる
- 一定の間隔で取り直す画面や、日付で表示が変わる画面を確かめる
- アプリのコンポーネントに testid を付ける

## 規則が止めないこと

ESLint の規則が止める書き方と、規則が拾わずにレビューで見るものは、`packages/e2e/DesignDoc.md` の「禁止する書き方」の表の「止め方」の列にある。  
options は `packages/e2e/eslint.config.mjs` で渡す。  
規則が拾わない操作(`screens/` の関数を `specs/<dir>/` の値のファイルで呼ぶなど)は、自分で避ける。

次のものは規則で判定できないので、書くときとレビューで見る。

- 「起きないこと」を、前後の確かめなしに確かめる。
- 読み込み表示が消えるのだけを待つ。
- ボタンを並びの位置で指す。名前で指す。
- 確定や削除の確認の画面を、文言を確かめずに押す。

## 待つ時間

spec に時間を書かない。全体と project の時間は Playwright の設定に、個別の時間は `fixtures/` の名前で置く。  
内側から `expect` < 操作 < 外部の読み込み(IdP のログインなど)< テストの全体の順に長くする。  
値を変えるときは、複数のパイプラインのテストごとの所要時間(CI のテストレポートにある、テストごとの実行時間)を集めて決める。

## 書いたら

1. `context/testing.md` の E2E の節にある lint と型のチェックを流す。
2. 書いた spec を 1 本だけ流す。
3. 期待を一時的に逆にして、落ちることを確かめてから戻す。落ちなければ、確かめ方を直す。
