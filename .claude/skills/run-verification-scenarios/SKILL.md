# run-verification-scenarios

撮るコマンドと格納先は、`context/testing/evidence.md`が持つ。置き場と名前は、`packages/e2e/kit/` の `evidence` が決める。  
このスキルは、撮るときと確かめるときの判断だけを持つ。

## 始める前に読むもの

- `context/testing/evidence.md`。撮るコマンド、環境変数、格納先、テストデータを作る手順
- 証跡の一覧(要求ごとの README など)。撮るシナリオ、spec を置かないシナリオ、撮影のための操作

## 利用者に確かめること

推測で埋めない。

1. 要求と、撮るシナリオ(全部か、絞るか)
2. 環境(ローカル環境か検証環境)と、改修前と比べるか
   - 比べないとき: 撮る環境の URL だけを渡し、1 つのバージョンを撮る
   - 比べるとき、`apps/web` だけの改修: 改修後と改修前の web を別のポートで起動し、1 回で両方を撮る。起動するブランチを確かめる
   - 比べるとき、`apps/*-api` も変わる改修と検証環境: 改修前と改修後の環境で 1 回ずつ流し、2 回目に 1 回目の実施日を渡して同じ置き場にそろえる。今どのバージョンがデプロイされているかを、アプリの画面で確かめる
3. テストデータを作ってあるか。作っていなければ、context にある手順で先に作る
4. 検証環境のログインの値と環境のファイルがあるか。値は環境のファイル以外のファイル、コミット、issue、pull request に書かない

## 撮る

1. テストデータが撮る日に依存するなら(今日の作業など)、その日に作り直す。
2. 1 つのシナリオを 1 本だけ流し、静止画で操作の位置と字幕が合うことを見てから、残りを流す。検証環境で初めて撮るときは、アクターごとに 1 本ずつ試す。
3. 残りを流す。出力をファイルに書きながら、バックグラウンドで流す。

- 録画は 1 本ずつ撮る。同じ端末でほかの撮影と同時に流すと、同じ置き場を書き合い、録画の速さも変わる。流す前に、ほかの Playwright の実行が無いかを確かめる。
- 時間切れで落ちた 1 本は、`-g` で絞って流し直す。
- ログインの状態を保存したアカウントを、並列の worker で共有しない。
- 撮影のためにデータを作る spec は、検証環境の共有のデータを一時的に変える。検証環境で撮る前に、利用者に伝える。
- 認証コードを求められたら、利用者に、待っているファイルへコードを書いてもらう。

## 確かめる

撮った spec ごとに、置き場のフォルダで次を見る。見た結果は利用者に報告し、判定(OK か NG か)はしない。判定は人が動画を見て行う。

1. README の表で、例の行ごとに mp4 がそろっているか
2. `frames/` の静止画で、字幕と画面が合っているか
3. 改修前と比べたときは、`compare/` の比較の画像で、縮尺、位置、画面が揃っているか。揃っていなければ、spec の待ちか操作の位置を直して撮り直す(直し方は write-verification-spec)
4. 録画の全体を 1 秒ごとの一覧で見て、失敗の通知、想定外のダイアログ、空白の画面が無いか

   ```sh
   ffmpeg -i <mp4> -vf "fps=1,scale=480:-1,tile=6x6" -frames:v 1 <作業の出力の置き場>/<名前>-sheet.png
   ```

5. 改修前と比べたときは、違う動きがシナリオの備考で違ってよいとされているか。書かれていなければ、利用者に示す

比較の画像が多いときは、サブエージェントに見せて、ずれている画像だけを挙げさせる。

## シナリオと食い違ったら

spec で無理に合わせない。利用者に、食い違った場面、静止画、直し方の案を示す。

- 期待の文が録画で判定できない: 期待の文を、画面で見分けられる結果に直す案を出す。
- 改修前も同じ不具合: 範囲外の不具合として起票するかを利用者に尋ねる。撮影では、字幕を付けて回避する。
- 改修前と改修後の差がシナリオに書かれていない: 備考に「違ってよい」と足す案を出す。

シナリオの直しは、検証シナリオの pull request のブランチで行い、pull request の本文の転記も同じ文に直す。

## 格納先へ上げる

- 格納先へ置く正式な証跡は、検証環境で撮ったものにする。ローカル環境で撮ったものは、検証環境で実施する前の確認に使い、置くかは担当者が決める。
- 置き場の `<アクター>/S<n>_<シナリオ名>/` のフォルダを、格納先の同じ名前のフォルダへ上げる。隠しフォルダの `.records/` は上げない。
- 上げた後に、検証シナリオの pull request に担当者、実施日、OK か NG かを書くのは人が行う。

## 終えたら

利用者に、次を伝える。

- 撮った環境、バージョン、シナリオと本数、通った本数と流し直した本数
- 確かめた結果(揃っていない比較の画像、失敗の通知、シナリオと食い違った点)
- 証跡の置き場
